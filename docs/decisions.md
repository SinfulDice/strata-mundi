# Décisions techniques

Une entrée courte par décision : contexte, choix, alternatives écartées. Les plus récentes en bas.

## D001 — Workspace et noms des crates (v0.1, jalon 0)

- **Contexte** : architecture en crates imposée par `CLAUDE.md`.
- **Choix** : un workspace Cargo (`resolver = "3"`, édition 2024) dont les crates se nomment `strata-<dossier>` (`strata-core`…) pour éviter les collisions avec des crates existantes (`core` est réservé par Rust). Le binaire du jeu s'appelle `strata`. Dépendances et lints déclarés une seule fois dans le `Cargo.toml` racine.
- **Alternatives écartées** : un seul crate avec modules (compilation plus lente, frontières client/serveur non garanties par le compilateur).

## D002 — Toolchain fixée (v0.1, jalon 0)

- **Choix** : `rust-toolchain.toml` épingle **Rust 1.97.0** (dernière stable au 23/10/2026). Mise à jour volontaire, dans un commit dédié.
- **Alternative écartée** : `channel = "stable"` (la CI changerait de compilateur sans prévenir).

## D003 — Lints de sécurité (v0.1, jalon 0)

- **Choix** : `unsafe_code = "deny"` et `clippy::unwrap_used`/`expect_used` en avertissement (donc bloquants avec `-D warnings`), autorisés dans les tests (`clippy.toml`). Un `unsafe` exigera une entrée ici et un `#[allow]` local.

## D004 — Formats de fichiers (v0.1, jalon 0)

- **Choix** : **TOML** (`toml` 1.x) pour ce que l'humain édite (options, touches), **RON** (`ron` 0.12) pour le contenu des packs, **postcard + zstd** pour les sauvegardes (bincode prévu à l'origine, abandonné : D026), **Fluent** pour les traductions. Tout passe par `serde`.

## D005 — Ligne de commande : `clap` (v0.1, jalon 0)

- **Contexte** : le binaire aura beaucoup d'options (`--screenshot`, `--seed`, `--pos`, `--look`, `--bench-scene`, `--preset`, `--texture-sheet`, `--render-icons`…).
- **Choix** : `clap` 4 (dérivation), crate de référence très maintenue ; aide générée automatiquement.
- **Alternative écartée** : analyse manuelle de `std::env::args` (beaucoup de code répétitif, messages d'erreur pauvres).

## D006 — Logs et profilage (v0.1, jalon 0)

- **Choix** : `tracing` + `tracing-subscriber` (filtre `RUST_LOG`, `info` par défaut, sortie sur stderr). Feature Cargo `profiling` qui ajoute `tracing-tracy` 0.12 : les spans `tracing` deviennent des zones Tracy, sans code spécifique. Tracy n'est jamais compilé dans les builds normaux.
- **Note** : `tracing-tracy` 0.12 embarque le client Tracy ; utiliser la version du profileur indiquée dans la documentation de `tracy-client` correspondante.

## D007 — CI, benchmarks et release (v0.1, jalon 0)

- **CI** (`ci.yml`) : fmt, puis clippy + tests + build release sur Ubuntu 24.04 et Windows.
- **Benchmarks** (`bench.yml`, séparé pour ne pas rendre la CI principale rouge à cause du bruit des machines partagées) : `criterion` sur le dernier tag `v*` (baseline `release`), puis sur `main` ; `scripts/bench-compare.sh` échoue si une moyenne ralentit de plus de 10 %.
- **Release** (`release.yml`, sur tag `v*`) : Linux compilé sur Ubuntu 22.04 (glibc plus ancienne, binaire plus portable) → `.tar.gz` et AppImage (`appimagetool`) ; Flatpak (`flatpak-builder`, runtime freedesktop 24.08) à partir du même binaire ; Windows → `.zip` et `.msi` (`cargo-wix`, WiX 3). Puis publication de la release et régénération de la branche orpheline `wiki` (force-push d'un seul commit).
- **Identifiant d'application** : `io.github.sinfuldice.StrataMundi`.

## D008 — Fenêtre, rendu et maths : `winit`, `wgpu` (Vulkan seul), `glam` (v0.1, jalon 1)

- **Choix** : `winit` 0.30 (fenêtre, clavier, souris ; référence de l'écosystème), `wgpu` 30 compilé **uniquement avec la feature `vulkan`** (plus `wgsl`), `glam` 0.34 (module `camera` pour les matrices). `pollster` pour attendre les quelques appels `async` d'initialisation, `bytemuck` pour envoyer les sommets sans `unsafe`.
- **Alternatives écartées** : backends GL/DX12/Metal (plusieurs chemins à tester), `nalgebra` (plus lourd), `cgmath` (peu maintenu).

## D009 — Rendu relatif à la caméra, reverse-Z, immediates (v0.1, jalon 1)

- **Caméra** en `f64` ; chaque maillage est dessiné avec son origine relative à la caméra, envoyée en **immediates** (ex-*push constants*, 16 octets par draw, feature `IMMEDIATES` requise : tous les GPU Vulkan la supportent). Pas de tremblement à 10 millions de blocs.
- **Reverse-Z + plan lointain infini** (`Depth32Float`, test `Greater`, effacement à 0) : précision de profondeur quasi uniforme, pas de z-fighting lointain.
- **Convention** : lacet 0 = nord (−Z), 90 = est (+X) ; tangage positif vers le haut ; Y vers le haut, repère main droite.
- **Alternative écartée** : décalage dans le uniform de caméra (une écriture de buffer par objet, inutilisable avec plusieurs objets dans une même passe).

## D010 — Manettes : `gilrs` (v0.1, jalon 1)

- **Choix** : `gilrs` 0.11 (Linux evdev, Windows XInput/WGI), boutons nommés par position (South/East…) donc indépendants de la marque. Facultatif : sans manette ou sans droits, le jeu tourne au clavier.
- **Couche d'actions** maison (`Action`, `Bindings`, `InputState`) : clavier en **codes physiques** (`KeyCode`), plusieurs liaisons par action, zone morte radiale de 15 %, dernier périphérique mémorisé pour les invites, tactile déjà prévu comme périphérique.

## D011 — Boucle de jeu et transport local (v0.1, jalon 1)

- **Serveur** sur son propre thread, horloge à pas fixe (`TickClock`, 20 TPS, rattrapage plafonné à 10 ticks). **Client** sur le thread principal (exigé par `winit`), rendu aussi vite que permis (VSync par défaut).
- **Transport solo** : canaux `std::sync::mpsc` typés (`ClientMessage`/`ServerMessage`, tous `Serialize`). `crossbeam-channel` n'est pas nécessaire tant qu'il n'y a qu'un producteur par sens.

## D012 — Captures et bench (v0.1, jalon 1)

- **Captures** : rendu hors écran (`Rgba8UnormSrgb`) puis relecture et encodage avec la crate `png` (légère, pure Rust ; `image` serait bien plus lourd).
- **Bench** : scènes en RON (`assets/bench-scenes/`), horodatage GPU par requêtes de timestamps lues en différé (4 emplacements tournants), mémoire et description de la machine via `sysinfo` 0.39 (multi-plateforme, maintenu), date via `chrono` (sans fuseau horaire embarqué). Rapport `perf-reports/<date>-<machine>-<profil>-<scène>.md`.
- **Headless** : en cloud, Mesa **lavapipe** suffit pour `--screenshot` ; la fenêtre et le bench se testent sous **Xvfb** (`xvfb-run`). Sous X11, `winit` charge `libxkbcommon-x11.so.0` à l'exécution (paquet `libxkbcommon-x11-0`).

## D013 — Format des packs (v0.1, jalon 2)

- **Choix** : un fichier RON par entrée (`blocks/<nom>.ron`), le nom du fichier donne l'identifiant ; un sous-dossier portant un namespace sert à **remplacer** l'entrée d'un autre pack ; `remove.ron` retire des entrées. Ordre de chargement : `priority` puis namespace. Erreurs collectées avec fichier, ligne et colonne ; jamais de plantage.
- **Remplacement complet** (pas de fusion champ par champ) : plus simple à comprendre, et les champs par défaut gardent les fichiers courts. Une fusion partielle pourra s'ajouter en v1.1 si le modding le demande.
- **Air** : intégré au moteur (`strata:air`, `BlockId` 0), non définissable par un pack.
- **Numéros de registre** attribués dans l'ordre alphabétique des identifiants, valables seulement en mémoire ; les sauvegardes stockeront les identifiants texte.

## D014 — Textures : palette globale + recettes (v0.1, jalon 2)

- **Choix** : toutes les couleurs viennent de **rampes nommées** d'une palette globale (`palette.ron`, fusionnée entre packs). Les textures sont des **recettes** RON (`Material`, `Overlay`, `Ore`, `Sprite`, `Recolor`) ou des PNG (16/32/64 px, agrandis au plus grand format présent, plus proche voisin). Un style complet = une palette ; c'est ainsi que sont produites les planches d'essai.
- **Bruit** maison (hachage entier + bruit de valeur périodique) : textures qui se répètent sans couture, identiques sur toutes les plateformes, sans dépendance.
- **Alternatives écartées** : PNG dessinés à la main uniquement (contraire à « généré par code ») ; couleurs écrites dans chaque recette (impossible de restyler le jeu d'un coup).

## D015 — Traductions : `fluent-bundle` (v0.1, jalon 2)

- **Choix** : `fluent-bundle` 0.16 (version `concurrent`, partageable entre threads) + `fluent-syntax` (liste des clés d'un fichier) + `unic-langid`. Le LOLcat utilise les règles de grammaire anglaises. Isolation Unicode désactivée (les marques invisibles s'afficheraient en carrés dans une police bitmap).
- **Clés** dérivées des identifiants : `block-strata-stone`, `item-…`, `category-…`.

## D016 — PNG dans `core` (v0.1, jalon 2)

- **Choix** : la crate `png` (déjà utilisée par le client) est aussi utilisée par `core` pour lire les textures des packs : `core` reste sans GPU et testable partout.

## D017 — Style des textures : « classique » (v0.1, jalon 2)

- **Contexte** : trois planches d'essai (classique, chaleureux, pastel) produites avec `--texture-sheet` sur le même échantillon (`docs/maquettes/`).
- **Choix de l'utilisateur (23/10/2026)** : style **1, classique** — tons naturels proches de Minecraft, contrastes moyens. Sa palette est celle de `assets/packs/strata/palette.ron`.
- Les deux autres palettes restent dans `docs/maquettes/styles/` comme exemples de packs de ressources.

## D018 — Sections à palette et maillage (v0.1, jalon 3)

- **Stockage** : palette par section + indices empaquetés dans des `u64` (0/1/2/4/8/16 bits, jamais à cheval sur deux mots, plus simple et aussi rapide). Section vide = aucun indice alloué. Colonnes de 32 sections.
- **Maillage** : face culling + fusion gloutonne + AO par sommet (4 niveaux, fusion seulement entre faces de même AO), diagonale choisie selon l'AO. Opaque/découpé et translucide séparés ; translucide trié par section, sans écriture de profondeur.
- **Sommet de 8 octets** (position 5+5+5 bits, face, AO, répétition UV, couche) décodé dans le shader ; origine de section en immediates. Alternatives écartées : sommets `f32` (28 octets), texture atlas (bavures aux bords, pas de répétition).
- **Threads** : `crossbeam-channel` 0.5 (file bornée multi-consommateurs, très maintenue) ; versions par section pour jeter les résultats obsolètes ; budget d'envoi GPU de 4 ms par image.
- **Benchmarks** : `criterion` sur une section de surface et sur le pire cas (damier).
- **Limites connues** : le translucide est trié par section, pas à l'intérieur d'une section (artefacts possibles entre deux surfaces d'eau d'une même section, à revoir avec les fluides en v0.2). Les sections enfouies (une seule sorte de bloc opaque, entourées de sections identiques) ne sont pas maillées. AO désactivée = coins tous éclairés, ce qui permet aussi plus de fusions.

## D019 — Génération : `fastnoise-lite`, climat à 4 cartes (v0.1, jalon 5)

- **Bruit** : `fastnoise-lite` 1.1 (portage officiel de FastNoiseLite, MIT, sans dépendance lourde) avec la feature `f64` pour la précision loin de l'origine. Alternative écartée : `noise` (plus lent, API plus lourde).
- **Modèle** : 4 cartes (température, humidité, continentalité, érosion) façon Minecraft 1.18. La hauteur ne dépend pas du biome (transitions sans falaise) ; biome = plus proche voisin dans l'espace climatique (continentalité pondérée ×3 pour garder les océans entiers), frontière légèrement bruitée. Montagnes = érosion faible × bruit en crêtes.
- **Contenu en packs** : `dimensions/`, `biomes/`, `features/` (arbres, piliers, minerais). `remove.ron` accepte ces catégories.
- **Déterminisme** : générateurs pseudo-aléatoires par colonne (SplitMix64 initialisé par graine + position + usage) ; les éléments de surface sont placés depuis les 9 colonnes voisines, dans un ordre absolu, pour ne pas dépendre de l'ordre de génération. Testé.
- **Grottes** : bruit 3D double sur grille 4×4×4 interpolée.

## D020 — Chargement du monde (v0.1, jalon 4)

- **Serveur** : disque de colonnes autour du joueur, priorité distance × orientation, file de génération bornée (4 travaux par thread), envoi limité à 48 colonnes/tick, déchargement avec 2 colonnes d'hystérésis. Les colonnes voyagent en `ServerMessage::Column(Box<Column>)` (structures `serde`).
- **Client** : maillage d'une colonne quand ses 8 voisines sont présentes (jamais de remaillage pour une voisine arrivée plus tard) ; frustum culling (plans latéraux + proche) ; le bench commence quand ~80 % du disque est chargé et maillé.
- **Distance verticale** : relevée (DS 4 sections, ultra 12) après essais, une valeur plus faible coupait les reliefs vus d'en haut.

## D021 — ECS maison (v0.1, jalon 6)

- **Choix** : entités à génération + un `Storage<T>` (sparse set) par composant + systèmes en fonctions libres, dans `server::ecs` (~200 lignes, tests compris).
- **Alternatives écartées** : `bevy_ecs` (lourd, API changeante, ordonnanceur inutile à 20 TPS), `hecs` (bien, mais le besoin v0.1 est un seul joueur ; on garde la main sur la sérialisation des sauvegardes). À réévaluer avec les mobs (v0.4) si les requêtes multi-composants deviennent nombreuses.

## D022 — Physique partagée, prédiction et réconciliation (v0.1, jalon 6)

- **Choix** : la physique du joueur (`core::physics::step`) est déterministe, à pas fixe (50 ms), et ne lit le monde qu'à travers une fonction « solide ? ». Client et serveur exécutent le même code.
- Le client applique chaque entrée tout de suite, l'envoie numérotée (`Input { sequence }`), puis repart de l'état officiel (`PlayerState`) en rejouant les entrées non confirmées. Rendu interpolé entre les deux derniers pas.
- **Anti-triche minimal** : entrées appliquées au rythme de l'horloge (réserve de rattrapage de 3), file bornée à 40, entrées non finies ignorées, chute automatique après 0,5 s sans entrée ; casser/poser : position validée avant tout calcul, portée (6 blocs serveur, 5 client), 10 actions/s au plus ; téléportation réservée au créatif. Solidité du monde (dessous, bordure, colonnes absentes) partagée : `physics::solid_at`.
- **Alternative écartée** : le client envoie sa position (jalons 1-5) — incompatible avec un serveur autoritaire.

## D023 — Interface maison déclarative (v0.1, jalon 6)

- **Choix** : écrans en RON (`assets/ui/`), nœuds ancrés + décalage en pixels d'interface, échelle entière automatique, comportement dans des `ScreenModel` Rust. Un seul atlas GPU (police, icônes, pixel blanc), un seul appel de dessin.
- **Police** : bitmap décrite en RON dans le pack (glyphes en `#`/`.`, accents composés automatiquement), donc remplaçable par pack de ressources. **Icônes** isométriques calculées sur CPU depuis les textures.
- **Alternatives écartées** : `egui`/`iced` (style difficile à rendre pixel art, navigation manette incomplète, dépendances lourdes) ; police TTF (`fontdue`) gardée pour la police d'accessibilité du jalon 8.
- Format interne jusqu'à la v1.1 (mods).

## D024 — Blocs orientés par variantes générées (v0.1, jalon 6)

- **Choix** : `placement: Axis` dans le pack ; au chargement, trois blocs du registre (`x`, debout, `z`) se partagent nom et objet, faces permutées. Le serveur choisit la variante d'après la face cliquée ; le mailleur tourne d'un quart la texture des faces longues (aucun octet de plus par sommet).
- **Alternative écartée** : états de bloc (propriétés par bloc stockées dans les chunks) — plus général mais coûteux en mémoire et en complexité ; les variantes « aplaties » sont ce que fait Minecraft depuis 1.13 et suffisent aux escaliers et dalles à venir.

## D025 — Fenêtre verticale glissante (v0.1, jalon 6)

- **Constat** : avec une distance verticale de 4 sections (DS), un joueur à 230 de haut ne voyait plus rien.
- **Choix** : la fenêtre verticale est centrée sur `min(section de la caméra, plus haute section non vide de la colonne)`. Sous terre rien ne change ; vu du ciel, chaque colonne garde ses sections de surface.

## D026 — Format des sauvegardes : `postcard` + `zstd` (v0.1, jalon 7)

- **Contexte** : `technique.md` prévoyait `bincode`, mais `bincode` 3.0 est publié comme crate abandonnée (plus maintenue) ; la règle « crate maintenue » l'emporte.
- **Choix** : `postcard` 1.1 (serde, format binaire compact et stable, très maintenu) pour les colonnes ; `zstd` 0.14 (niveau 3) colonne par colonne ; RON lisible pour `world.ron` et `player.ron`.
- **Régions** de 32×32 colonnes : un fichier `r.<x>.<z>.region` (en-tête `SMRG` + postcard) ne contient **que les colonnes modifiées**, compressées une à une ; les autres sont régénérées depuis la graine. Les blocs sont stockés par **identifiant texte** (palette par colonne), donc un monde survit à l'ajout ou au retrait de packs (bloc disparu → air).
- **Écriture atomique** (fichier temporaire, `fsync`, renommage, `fsync` du dossier) ; région illisible mise de côté en `.damaged` au lieu d'être écrasée ; colonnes relues validées (`Column::remapped`), jamais de panique sur un fichier abîmé.
- **Versions** : `FORMAT_VERSION` dans `world.ron` ; autre version → statut « trop ancien / trop récent » dans la liste, pas d'ouverture. Pas de migration en 0.x (règle du projet), donc pas encore de « copie avant migration » : elle viendra avec la première migration (v1.0). Les copies tournantes (3 par défaut) sont faites à chaque ouverture d'un monde.
- **Dossiers** : `dirs` 7 (emplacements standard Linux/Windows), surchargeable par `--data-dir`.

## D027 — Menus : pile de menus, modèles et lanceur (v0.1, jalon 7)

- **Pile** de menus (`Menu`), chaque menu = une disposition RON + un modèle Rust ; les modèles ne font qu'émettre des **effets** (ouvrir, fermer, action) que `Screens` et la session appliquent. Les actions qui touchent aux mondes passent par le trait **`Launcher`** fourni par `app` : le client ne lit ni n'écrit aucun fichier de sauvegarde.
- **Étapes** de la session : écran titre (panorama généré hors serveur, graine fixe) ou monde en cours (connexion + fil du serveur, rejoint en quittant pour que tout soit écrit avant de revenir à la liste).
- **Captures des mondes** : rendu hors écran 96×54 au format de la fenêtre, envoyé au serveur dans `Save { icon }` ; affichées depuis des emplacements réservés de l'atlas d'interface (mis à jour par `write_texture`).
- **Options d'interface** dans `config/interface.toml` (langue, échelle, pause dans tous les menus, disposition du HUD) ; le fichier de réglages complet du jalon 8 les reprendra.
- **Boutons de manette** nommés comme sur la New 3DS (A droite, B bas) ; les invites suivent le dernier périphérique et, au clavier, la lettre réellement imprimée (apprise à la frappe).

## D028 — Veille du DS : `zbus` (v0.1, jalon 7)

- **Choix** : `zbus` 5 (D-Bus en Rust pur, très maintenu, API bloquante), Linux uniquement (`cfg(target_os = "linux")`), sur un fil dédié : verrou de retardement logind + signal `PrepareForSleep`. Sans logind, simple message dans le journal.
- **Alternatives écartées** : lancer `dbus-monitor`/`gdbus` (fragile, dépend d'outils absents d'un Linux minimal), `dbus` (lie `libdbus` en C).

## D029 — Fichier de réglages unique (v0.1, jalon 8)

- **Choix** : `config/settings.toml` remplace `interface.toml` ; quatre sections (`graphics`, `interface`, `controls`, `game`) et un `preset` (absent = « personnalisé »). Toute valeur manquante ou invalide reprend sa valeur par défaut, le reste du fichier est gardé. Les touches sont écrites par action (`MoveForward = [{ Key = "KeyW" }, …]`) pour rester modifiables à la main.
- **Application à chaud** : l'écran d'options modifie une copie ; chaque image, la session la compare à la copie en vigueur et ne refait que ce qui a changé (re-maillage, échantillonneur, VSync…).
- **Passe finale** (`render/post.rs`) uniquement si l'échelle de rendu ≠ 100 % ou si un filtre daltonien est actif : coût nul sinon. Filtres : méthode « daltonize » de Fidaner, Lin et Ozguven (simulation LMS, puis report de l’écart vers des couleurs distinguables).
- **Option `--preset`** : appliquée au lancement sans être écrite, sauf si le joueur modifie ensuite un réglage.

## D030 — Mises à jour et plantages : `ureq` et `open` (v0.1, jalon 8)

- **Vérification de mise à jour** : `ureq` 3 (client HTTP bloquant, petit, maintenu, rustls) sur un fil à part, une requête à l'API GitHub des releases, délai 8 s, certificats du système (`platform-verifier`). Désactivable ; rien n'est envoyé hormis la requête elle-même.
- **Rapports de plantage** : crochet de panique qui écrit `crash-reports/crash-<date>.txt` (version, système, message, pile d'appels, 60 dernières lignes du journal gardées en mémoire). Au lancement suivant, l'écran titre propose « Signaler ce plantage » : `open` 5 ouvre le navigateur sur une issue GitHub pré-remplie (adresse limitée à ~6 000 caractères). Jamais d'envoi automatique.
- **Alternatives écartées** : `reqwest` (tire `tokio`), `webbrowser` (équivalent, moins utilisé).

## D031 — Police lisible : `fontdue` (v0.1, jalon 8)

- **Choix** : `fontdue` 0.9 (rastériseur TrueType en Rust pur, sans dépendance C, très rapide) ; la police (DejaVu Sans, licence libre propre) est rastérisée au chargement dans le même atlas que la police pixel, à la **densité de l'écran** (échelle d'interface ×1 à ×3, moins si l'atlas de 512 px ne suffit pas). Le dessin du texte accepte des positions fractionnaires en pixels d'interface.
- **Alternatives écartées** : `ab_glyph` (équivalent, un peu plus lent), `cosmic-text` (mise en page complète, beaucoup plus lourd, inutile pour du texte d'interface court).

## D032 — Console : commandes exécutées par le serveur, réponses traduisibles (v0.1, jalon 8)

- **Choix** : la ligne tapée part telle quelle (`ClientMessage::Command`) ; le serveur l'analyse et répond par `Feedback { key, args, error }` (clé Fluent + arguments), jamais par du texte. La table des commandes (`protocol::commands`) est partagée pour l'aide et la complétion côté client. `/help` et `/cinematic` restent côté client (rien à décider pour le monde).
- **Heure du monde** : `day_time` dans `world.ron` (`#[serde(default)]`, compatible avec les mondes existants), journée de 24 000 ticks (20 min) ; le ciel la suivra en v0.2.
- **Alternative écartée** : analyser côté client et envoyer des messages typés par commande — chaque nouvelle commande toucherait le protocole, et le serveur doit de toute façon tout revérifier.

## D033 — Cinématiques en packs (v0.1, jalon 8)

- **Choix** : `cinematics/<nom>.ron` (points clés temps/position relative/angles, sous-titre optionnel en clé de traduction, `skippable`, `letterbox`), trajectoire Catmull-Rom, angles par le plus court chemin, validés au chargement (au moins deux points, temps croissants, valeurs finies). Lecture côté client, joueur immobile pendant le plan.
- **Plus tard** : déclenchement par le serveur (boss, découvertes) avec un message dédié ; le format ne changera pas.

## D034 — Wiki : `wikigen`, `pulldown-cmark`, `serde_json` (v0.1, jalon 9)

- **Choix** : binaire `wikigen` qui charge les packs comme le jeu et écrit un site statique par langue ; gabarits inclus dans le binaire (`include_str!`), aucun moteur de gabarits. `pulldown-cmark` 0.13 (Markdown → HTML, référence de l'écosystème, sans dépendance lourde) pour les textes ; `serde_json` pour l'index de recherche, servi en `.js` (`window.SEARCH_INDEX = …`) pour fonctionner depuis `file://`.
- **Données jamais recopiées** : infobox, lieux de génération, commandes, touches et réglages viennent des packs ou des tables du jeu (`strata_client::catalog`, `protocol::commands`).
- **Images** : PNG plutôt que WebP (pas d'encodeur WebP sans dépendance C) ; icônes calculées sur le processeur, vues de biomes rendues par le jeu (lavapipe en CI).

## D036 — Relief par densité 3D et courbes de climat (v0.2, jalon 1)

- **Choix** : comme Caves & Cliffs, la hauteur « plate » vient de **courbes** (`Spline`, points lissés) de la continentalité, de l'érosion et des « pics et vallées » (bruit de bizarrerie replié) ; les courbes sont dans le pack (`dimensions/terra.ron`, bloc `relief`), seule la façon de les combiner est dans le code. Un bloc est plein si `hauteur − y + surplomb × bruit3D > 0` : l'amplitude du surplomb dépend de l'érosion (falaises, arches et surplombs en montagne, rien en plaine ni dans les rivières).
- **Grille alignée sur le monde** : le bruit 3D est échantillonné tous les 4 blocs (8 en hauteur) sur une grille globale puis interpolé ; la hauteur de surface d'un point quelconque se recalcule donc **exactement** (`Generator::surface_height`), ce qui garde les arbres des colonnes voisines posés sur le vrai sol.
- **Plateaux** : bande d'érosion relevée et découpée en terrasses (falaises de plateau, mesas). **Pentes raides** (≥ 3 blocs entre voisins) en roche nue (`steep` réglable par biome).
- **Rivières** : ligne zéro d'un bruit dédié, lit sous la mer (eau au niveau de la mer), berges lissées, estompées en altitude (vallées sèches). Biome `river` choisi seulement sur le lit (`river: true`) ; les biomes peuvent exiger une plage de hauteur (`min_height`, `max_height`).
- **Packs** : l'extension RON `implicit_some` est activée pour tous les fichiers de pack (`steep: "strata:stone"` au lieu de `Some(...)`).
- **Alternative écartée** : densité 3D complète sur toute la hauteur (comme Minecraft) — 10 à 20 fois plus de bruit 3D à calculer, alors que seule une bande autour de la surface en a besoin.

## D037 — Grottes : tunnels, nouilles, cavernes, ravins, aquifères et lave (v0.2, jalon 2)

- **Choix** : grottes creusées après le relief (module `worldgen/caves/`), comme Caves & Cliffs : **spaghetti** (deux bruits 3D proches de zéro), **nouilles** (même idée, plus fines, sous `noodle_top`, une moitié de l'espace via un bruit d'activation), **cavernes « fromage »** (un bruit au-dessus d'un seuil qui baisse avec la profondeur, rien au-dessus de y ≈ 180) avec **piliers** là où un bruit étiré verticalement monte, **ravins** en V (ligne zéro d'un bruit 2D sous un masque rare ; certains s'ouvrent en surface, d'autres restent entre y ≈ 0 et 80). Bruits 3D sur une grille alignée sur le monde (pas de 4) interpolée ; `at_point` redonne la même valeur pour un seul bloc (les arbres des colonnes voisines ne poussent pas au-dessus d'une entrée de grotte).
- **Toits** : sur terre ferme (les 9 voisins au moins 3 blocs au-dessus de la mer), tunnels et ravins montent jusqu'à la surface (entrées) ; ailleurs, 9 blocs sous le plus bas voisin ; cavernes toujours 12 blocs sous le plus bas voisin. Jamais de socle, d'eau, de glace ni de lave creusés : aucune grotte n'ouvre une mer ou une rivière (test sur côtes et rivières).
- **Aquifères** : cellules de `aquifer_cell` (64) blocs dans un espace déformé par bruit (frontières sinueuses), une part (`aquifers`) a un niveau d'eau plat tiré entre `aquifer_top − aquifer_depth` et `aquifer_top` (borné à mer − 4) ; un mur de roche de 2 blocs de chaque côté des frontières, seulement entre les deux niveaux (depuis le fond si une cellule est sèche), empêche l'eau de pendre. **Lave** dans tout ce qui est creusé sous `lava_level` (10). Les fluides restent statiques jusqu'au jalon 5.
- **Réglages** : bloc `caves: (...)` du pack (remplace `caves: bool`, absent = pas de grottes), `enabled` pour couper, `density` multiplie toutes les largeurs et ramène le seuil des cavernes vers 1 (0 = aucune grotte), seuil final borné à 0,15 minimum ; profondeurs des ravins et hauteur des cavernes aussi dans le pack ; valeurs bornées au chargement. Le départ du joueur évite les entrées de grottes (bloc plein dessous, rien de creusé sur 4 blocs autour).
- **Coût** : 1,8 ms par colonne au banc (`generate_column`), 2,9 ms en montagne, 1,4 ms sur une caverne.
- **Ravins revus (v0.2.1, jalon 1)** : l'ancien masque autorisait des ravins sur près de la moitié du monde, larges, en V aux parois en escalier couvertes d'herbe (« rigole verte » en forêt). Désormais façon canyons de Minecraft : le monde est découpé en carrés de `ravine_spacing` blocs (pack, 320), chacun avec **un** ravin légèrement courbé (longueur 25 à 45 % du carré, extrémités effilées et moins profondes), étroit (`ravines` devient une **demi-largeur en blocs**, 3,5, ×0,75 à ×1,25), parois quasi verticales (rétrécissement en puissance 4 vers le fond, à 30 %) avec de petites corniches par couche ; 35 % restent cachés sous terre. Environ 0,6 % de la surface au-dessus d'un ravin (test : entre 0,05 et 2 % sur 4 graines). Les colonnes à moins de 1,5 bloc d'un ravin ouvert (et dedans) perdent leur sol (surface et sous-sol du biome → roche raide du biome ou pierre) ; aucun bloc d'arbre ou de pilier (tronc, feuilles) à moins de 4 blocs du bord le plus large d'un ravin ouvert (marge de la racine = 4 + rayon réel de la couronne), départ du joueur aussi ; un ravin caché ne masque jamais un ravin ouvert (tous les ravins proches sont testés). **Rupture** : `ravines` change d'unité (0,03 de bruit → 3,5 blocs) ; un pack qui garde une valeur < 1 reçoit un avertissement au chargement. Les ravins proches sont trouvés une fois par colonne (`Ravines::around`, élargi de la portée des arbres voisins) et partagés entre creusement, parois et arbres : bancs inchangés (mesurés avant/après sur la même machine). Le ravin ne se voit pas sur `--map` (hauteurs sans grottes). Alternative écartée : garder la ligne zéro d'un bruit sous un masque plus sélectif (lignes infinies, fréquence difficile à borner).
- **Alternative écartée** : grottes « vers » de l'ancien Minecraft (marcheurs aléatoires) — dépendent des colonnes voisines et de l'ordre de génération, plus coûteuses à garder déterministes.

## D038 — Cuivre et grands gisements de minerai (v0.2, jalon 3)

- **Choix** : cuivre (`copper_ore`, `deep_copper_ore`) en petits filons comme les autres minerais (ajouté en fin de liste `ores` pour ne pas décaler les sels des minerais existants). **Grands gisements** : nouveau type de feature `Deposit` (module `worldgen/deposits/`), listé dans `deposits` de `terra.ron` (liste vide = aucun gisement). Le monde est découpé en cellules de `cell` (256) blocs ; un hachage (graine, cellule, feature) décide si la cellule a une veine (`chance` 0,4), son centre (hauteur entre `min_y` et `max_y`), sa longueur (40-80), son épaisseur (6-10), son cap et une inclinaison de ±14°. Forme : lentille autour d'un segment (rayon 30 % aux bouts, 100 % au milieu) gonflée de ±35 % par un bruit 3D ; chaque bloc de pierre/roche profonde dedans devient minerai (`ore_share` 35 %, tirage par bloc) ou roche de remplissage. Fer : **roche ferrugineuse** (rouille) ; cuivre : **roche vert-de-gris**. Variantes profondes du minerai dans la roche profonde ; `deep_filler` optionnel.
- **Signes** : au-dessus de l'empreinte horizontale de la veine (quelle que soit sa profondeur), `sign_share` (5 %) des blocs de surface listés dans `sign_on`, à l'air libre (jamais sous l'eau), deviennent le bloc `sign` (ici la roche de remplissage) : traînée discrète de taches colorées.
- **Ordre** : relief → grottes → petits filons → gisements → arbres ; les gisements ne remplacent que pierre et roche profonde (test avec/sans gisements). Déterminisme : chaque colonne relit les cellules qui peuvent l'atteindre, sans état partagé.
- **Bornes au chargement** : longueur 8-128, épaisseur 2-24, cellule 64-4096, parts 0-1 (signes ≤ 0,5), hauteurs dans le monde. Variante `Deposit { ... }` en struct (l'extension RON `unwrap_variant_newtypes` casse `Some((...))` des packs existants).
- **Coût** : banc `generate_deposit_column` (colonne au centre d'une veine) 2,8 ms, autant que la même colonne sans gisement (le relief y est coûteux) : filtre horizontal par bloc de surface, hauteurs restreintes autour du segment, bruit 3D seulement près du bord. Plaine 1,9 ms, caverne 1,5 ms ; montagne 3,0-3,3 ms selon la charge de la machine (chemin inchangé, le banc varie de ±10 % ici).
- **Stabilité** : les sels d'une veine (cellule, minerai, signes) viennent d'un hachage FNV-1a de l'identifiant de la feature, pas de son rang : ajouter ou retirer d'autres features ne déplace aucun gisement. Un gisement qui nomme un bloc inconnu est rejeté (erreur de pack), jamais de veine d'air.
- **Arbres sur les signes** : les arbres passent après les signes et testent le bloc de surface d'origine ; un arbre peut donc pousser sur un signe, ce qui reste discret et est accepté.
- **Alternative écartée** : gisements comme gros filons aléatoires par colonne — limités à la colonne (ou à ses voisines), ils ne peuvent pas atteindre 80 blocs ni laisser des signes cohérents en surface.

## D039 — Végétation en croix et touffes de plantes (v0.2, jalon 4)

- **Rendu** : nouveau `RenderKind::Cross` : deux plans diagonaux (texture de la face nord), émis par `mesher/cross.rs` dans le maillage opaque/découpé (rejet alpha du shader existant). Chaque plan est émis **deux fois** (un quad par sens) plutôt que de créer un pipeline sans culling : un seul pipeline, coût de 8 sommets de 8 octets par plante. ## D042 — Fluides : variantes de bloc, file de blocs actifs et mises à jour de voisinage (v0.2, jalon 5)

- **Variantes plutôt qu'état de bloc** : champ `fluid: (tick_rate, spread, slope_search, renewable, hardens)` d'un bloc du pack ; au chargement, la source génère `<nom>__1` … `<nom>__<spread>` (écoulement, 1 = le plus plein) et `<nom>__falling` (chute), sans objet ni catégorie, nommés comme la source (`Block::family`). `Block::fluid: Option<FluidState { source, level: Source | Flowing(n) | Falling }>`, `Content::fluids` (par source) donne le bloc de chaque niveau. - **Simulation dans `core`** (`core::updates`, testable sans serveur) derrière un trait `BlockAccess` (bloc, écriture, limites) : le serveur l'implémente sur les colonnes chargées bornées par la bordure (`loader::Bounded`). **File de blocs actifs** `BTreeMap<(tick, ordre), pos>` + table des positions planifiées (la plus proche planification gagne) : aucun balayage, ordre déterministe. Règles proches de Minecraft : niveau voulu d'après les voisins (au-dessus du même liquide = chute ; sinon 1 + le plus plein des 4 côtés ; au-delà de `spread` = assèchement) ; chute prioritaire ; sinon étalement d'un niveau vers les côtés qui mènent au trou le plus proche (BFS limité à `slope_search`), tous les côtés ouverts si aucun ; une chute qui tombe dans son propre liquide ne s'étale pas ; deux sources voisines sur un sol (ou une source) créent une source (`renewable`) ; lave touchant l'eau (dessus ou côtés) → obsidienne (source) ou pierre, lave qui tombe sur l'eau → pierre. Les liquides emportent air et plantes (`replaceable`, `rooted`, `hanging`).
- **Mises à jour de voisinage générales** : `BlockUpdates::set_block` écrit, puis les 6 voisins réagissent (liquides planifiés à `tick_rate`, plantes enracinées sans sol et blocs suspendus — nouveau champ `hanging`, la liane — sans plafond solide ou identique retirés, en cascade) ; tous les changements partent au client comme avant. Remplace le retrait spécial de D039 ; la pose d'une plante vérifie son support (sol ou plafond).

## D043 — Rendu des liquides, nage partagée et seau créatif (v0.2, jalon 5)

- **Surface inclinée** : hauteur d'une case en seizièmes, commune au mailleur et à la physique (`content::surface_sixteenths`) : source 14, écoulement `14 − ⌈12 n / 7⌉` (12 → 2), chute 16. Hauteur d'un coin = moyenne des cases de la **même famille** autour (jusqu'à 4), pleine si l'une a le même liquide au-dessus (cascades continues). Un liquide ne dessine jamais une face partagée avec sa famille ; un liquide surmonté de lui-même est plein. Faces inclinées jamais fusionnées (`single`), surfaces plates (océans) toujours fusionnées. Pas d'AO sur les liquides.
- **Liquide opaque (lave)** : cache la face du dessus du bloc en dessous, et les faces de côté seulement quand il est plein ; sinon on verrait le vide au-dessus d'une surface basse. Le dessus d'un liquide reste dessiné sous un bloc opaque quand il est abaissé.
- **Sommet** toujours de 8 octets ; second mot : `layer:16 drop:4 animation:2 libre:2 lumière:8` (les 8 bits de lumière ciel/bloc sont réservés au jalon 6). `drop` abaisse le sommet en seizièmes ; sur les côtés, `v` est décalé d'autant pour garder l'échelle de la texture.
- **Animation** : temps en uniforme (`effects.x`, bouclé à 3 600 s) ; dessus : défilement lent + ondulation dans le fragment ; côtés : défilement vers le bas. Vitesse par code (`Ripple` eau, `Ooze` lave lente, `Still`) choisie dans le pack (`fluid.view.animation`). Réglage graphique `liquid_animation` (coupé en très bas) : force 0 en uniforme, aucun remaillage. Passe translucide **sans élimination des faces arrière** : la surface reste visible depuis dessous.
- **Vue immergée** : œil sous la surface d'un liquide (client) → brouillard sur la distance 3D, de la couleur du liquide (`fluid.view.fog_color`, `fog_distance` : eau 12 blocs, lave 2,5), commençant à −0,5 × distance derrière la caméra pour teinter aussi le proche, fond de la même couleur. Indépendant du réglage brouillard (information de jeu, coût nul).
- **Nage** (`core::physics::swim`, même code client et serveur via un trait `Terrain` : solidité + liquide par case ; une simple fonction de solidité reste un `Terrain` sans liquide) : immergé si la boîte touche une case dont la surface est au-dessus des pieds ; le liquide le plus épais l'emporte. Paramètres du pack `fluid.motion: (speed, drag, gravity)` : eau 0,5 × marche, 0,8, 0,15 (on coule à ~1 m/s, on remonte à ~2,2 m/s saut maintenu) ; lave 0,25, 0,5, 0,25. Contre une berge dont le dessus est libre 0,6 bloc plus haut : poussée de 6 m/s (Minecraft). Le vol créatif ignore les liquides.
- **Seau** : objets `bucket` (`action: TakeFluid`), `water_bucket` et `lava_bucket` (`PlaceFluid(source)`) dans la nouvelle catégorie `strata:tools`. Message `UseItem { item, against, face }` ; le serveur vérifie que l'objet est dans la barre, la portée, la cadence, puis pose la source (même cible que la pose d'un bloc) ou retire une source visée, par `BlockUpdates::set_block` (l'écoulement suit). Côté client, seul le seau vide vise les sources (boîte pleine). En créatif le seau ne change pas. Le serveur exige l'objet dans **la case choisie** (pas seulement dans la barre) et refuse le seau hors créatif (aucun retour au joueur : `UseItem` n'a pas de réponse) tant que la survie (v0.3) ne lui donne pas de contenu.
- **Captures** : option `--scene <nom>` (diorama `assets/scenes/<nom>.ron`, sans `--seed`) ; scène `fluids` (cascade, écoulement, lave, étang).
- **Coût** : banc `mesh_section_flowing_water` (terrain inondé à tous les niveaux) ~0,23 ms. Le terrain sans liquide coûte ~+6 % d'instructions (callgrind) et +10 à 15 % de temps mesuré ici : les sections dont la palette n'a aucun liquide sautent les tests de liquide (`mesh_faces::<false>`), la clé de fusion est passée de 14 à 6 octets. À surveiller par l'alerte des bancs.
- **Alternatives écartées** : passe séparée pour les liquides (comme les plantes) — les faces de liquide doivent participer au masquage des voisins, et les océans plats se fusionnent mieux dans la passe gloutonne ; sommet de 12 octets (mémoire GPU +50 % pour 6 bits).

## D044 — Bateaux : entités génériques, physique partagée, rendu de modèles en boîtes (v0.2, jalon 5)

- **Types d'entité en pack** : `entities/<nom>.ron` (`Entity(model, texture, size: (largeur, hauteur), boat: Some(Boat(...)))`) et `models/<nom>.ron` (boîtes en seizièmes autour de l'origine, avant vers −Z), registre `EntityTypeId` dans `Content`, retirables par `remove.ron`. Cinq bateaux (chêne, sapin, bouleau, jungle, acacia) partagent le modèle `strata:boat` et prennent la texture de leurs planches. Objets bateau : `action: PlaceEntity(<entité>)`, catégorie `strata:transport`, sprites (chêne dessiné, autres en `Recolor`).

Flottaison : surface la plus haute sous l'empreinte (cases de liquide remontées jusqu'à 32), vitesse verticale amortie vers `surface − draft` ; ne coule jamais, remonte s'il est immergé. Horizontal façon Minecraft : `v = v × élan + poussée` ; élan `water_momentum` (0,9) sur l'eau et en l'air, **glissance du bloc** dessous au sol (`slipperiness` de bloc, 0,6 par défaut, glace 0,98) : ~8 m/s sur l'eau, 2 m/s à terre, jusqu'à 40 m/s (plafond) sur la glace. Trait `Terrain` : méthode `slipperiness` par défaut.
- **ECS serveur** : composants `boats` (type, corps, commandes du pilote, pilote, dernier état envoyé) et `mounts` (joueur → bateau). Le système des joueurs fait piloter le bateau par les entrées d'un joueur assis (`wish[1]` avance/recule, `wish[0]` tourne) et ne bouge plus son corps ; une **nouvelle** pression d'accroupi demande la descente (tenir accroupi en montant n'éjecte pas). Système des bateaux : un pas par tick, le cavalier est posé au siège (`seat`). Descente : rive libre et portante à côté (côtés, puis arrière, avant ; au niveau de l'eau ou un bloc plus haut), sinon sur le bateau. Monter : clic droit sur un bateau libre à portée (point le plus proche de la boîte) ; retirer : clic gauche en créatif. 512 bateaux au plus. **Veille** : un bateau sans pilote immobile pendant 20 ticks (à flot stable ou posé) n'est plus simulé ; il se réveille quand un bloc à moins d'un bloc de sa boîte change (joueur ou écoulement) ou quand on y monte (pas encore de collisions entre entités pour le « heurter »).
- **Protocole** (version 3) : `NetEntity(u64)` = index | génération << 32 (jamais réutilisé ; un identifiant forgé ne trouve rien), `EntitySpawned(EntityState)`, `EntityMoved` (seulement si position ou cap a changé), `EntityRemoved`, `Mounted(Option<NetEntity>)` ; intentions `InteractEntity`, `AttackEntity`, pose par `UseItem`. Toutes les entités sont envoyées à l'arrivée (pas encore de filtrage par distance : à revoir avec les créatures).
- **Client** : pas de prédiction du bateau (latence d'un tick en solo, acceptable pour un bateau) ; `ClientEntities` interpole position et cap (chemin le plus court) entre les deux dernières poses sur un tick. Le joueur assis ne prédit plus son corps (pas de rejeu) ; ses yeux suivent la pose interpolée du bateau + siège, la vue reste libre. Visée : rayon contre les boîtes des entités, retenue si plus proche que le bloc visé ; le bateau monté est ignoré. HUD : rappel « <Accroupi> : descendre du bateau » (élément `mount`, déplaçable).
- **Rendu des modèles** : `ModelLibrary` (quads de boîtes, UV en blocs, ombrage par face comme les blocs) ; chaque image, les modèles visibles (sphère englobante contre le frustum) sont placés relativement à la caméra sur le CPU et dessinés en **un seul appel** (`model.wgsl`, mêmes groupes caméra/textures que les blocs, brouillard identique), après les blocs opaques et avant l'eau. Coût négligeable (252 sommets par bateau).
- **Sauvegarde** : `entities/<espace>/<dimension>.ron` (`Entities(boats: [Boat(kind, position, yaw)])`, identifiants texte) ; absent = aucun bateau (mondes existants compatibles, format inchangé) ; `player.ron` gagne `boat: Option<index>` (`#[serde(default)]`) pour se rasseoir au chargement.
- **Alternatives écartées** : prédiction client du bateau (rejeu de deux corps, réconciliation compliquée, gain faible en solo) ; boîte de collision tournée (OBB) ; maillage GPU par type avec matrice par instance (plus de code de pipeline pour une poignée d'entités).

## D045 — Lumière : donnée dérivée, moteur pur dans `core`, calcul client sur un thread dédié (v0.2, jalon 6)

- **Répartition** : la lumière se déduit des blocs, elle n'est ni sauvegardée ni envoyée par le réseau. Moteur pur `core::light` (testable sans GPU) ; le **client** la calcule pour le rendu (il n'écrit toujours pas dans le monde : la lumière n'est pas un état du monde) ; le serveur réutilisera le même moteur en v0.4 (apparition des monstres selon la lumière), via le trait `BlockSource`. Calcul côté serveur puis envoi écarté : 4 Kio par section mixte à transmettre et à garder en double, pour une donnée que le client sait reconstruire.
- **Règles** (façon Minecraft, lumière blanche 0-15) : la lumière du ciel 15 **descend sans perte** dans les blocs d'opacité 0 (`15 − opacité` vers le bas depuis 15), sinon chaque pas coûte `1 + opacité` du bloc atteint ; la lumière des blocs part de `light_emission` (pack, 0-15) avec la même perte. Le haut du monde (y = 511) est source du ciel. Opacités du pack : feuilles 1, eau et glace 2, verre, plantes, torche et lanterne 0, lave et blocs pleins 15. Émissions : torche 14, lanterne, pierre lumineuse et lave 15.
- **Stockage** : un octet par bloc (ciel en 4 bits hauts, bloc en 4 bits bas), `SectionLight::Uniform` (aucune allocation : ciel ouvert au-dessus du terrain, roche noire dessous) ou `Mixed(Arc<[u8; 4096]>)` partagé avec les copies envoyées au rendu (copie à l'écriture). Recompactage en uniforme après le calcul initial.
- **Calcul initial d'une colonne** : sections au-dessus du plus haut bloc = ciel 15 sans calcul ; puits de ciel verticaux jusqu'au premier bloc qui atténue ; lampes ; puis flood fill semé **seulement** là où la lumière peut encore bouger (bords des puits plus bas à côté, premier bloc atténuant, lampes, échange des faces partagées avec les colonnes voisines déjà éclairées, dans les deux sens, en sautant les sections uniformes identiques). Le résultat ne dépend pas de l'ordre d'arrivée des colonnes (testé).
- **Mise à jour incrémentale** : à chaque bloc changé (avec l'ancien bloc ; un canal sauté si opacité et émission sont inchangées), retrait puis ajout en deux files comme Minecraft : le retrait éteint tout voisin dont la lumière a pu venir de la case (`niveau ≤ atténuation`), met en file d'ajout le bord plus lumineux et les sources rencontrées ; l'ajout relit la valeur courante à chaque sortie de file. La lumière ne se propage que dans les colonnes éclairées, à travers leurs frontières. Sections signalées : celles dont la lumière **ou la bordure d'un bloc** a changé (pour le remaillage lissé). Tests : poser puis casser une torche = toutes les valeurs identiques (aussi à cheval sur deux colonnes), 120 modifications aléatoires = recalcul complet.
- **Client** : thread `lighting` dédié (et non les threads de maillage : la propagation est séquentielle sur une carte partagée). Il reçoit les colonnes en `Arc<Column>` **partagées** avec `ClientWorld` (copie seulement quand un bloc change, au plus une fois par colonne et par image : les changements de l'image sont regroupés) et éclaire une colonne quand ses 8 voisines sont là, comme le maillage. Il renvoie les sections changées ; `ClientWorld` les garde (ciel ouvert là où rien n'est arrivé) ; le travail de maillage emporte les 27 `SectionLight` autour de la section (copies d'`Arc`) et le thread de maillage en tire la lumière par case (`Neighborhood::resolve_light`), rien n'est recopié sur le thread de rendu. Les sections touchées sont remaillées. **Lots bornés** (16 travaux ou 4 ms) : un résultat partiel part après chaque lot ; les changements de blocs et les retraits passent avant les colonnes à éclairer, sans réordonner les travaux d'une même colonne (un changement pour une colonne en attente est fusionné dans son insertion). Une colonne renvoyée par le serveur alors qu'elle est éclairée est recalculée (`remove_column` puis éclairage). Arrêt : drapeau `AtomicBool` vérifié avant chaque travail (fermer un monde n'attend pas la file). Thread mort : signalé une fois (`error`), le monde passe en éclairage plat et `is_idle` ne bloque plus les bancs.
- **Hachage** : `ColumnMap` (hachage multiplicatif façon `FxHasher`, sans crate) pour les cartes par colonne du moteur : le hachage par défaut représentait plus de la moitié du coût de propagation.
- **Coût** (cloud) : 1,2 ms par colonne générée (voisines éclairées), 0,65 ms pour poser puis casser une torche en plein air ; après la relecture (curseur de blocs qui garde la dernière colonne dans `spread`/`unspread`, colonnes lues une fois par face dans l'échange des bords) : 1,04 ms et 0,60 ms. Le thread `lighting` compte dans les threads de travail : un thread de maillage de moins s'il y en a au moins deux.
- **Réglage « Éclairage »** (`graphics.lighting`) : complet ou **plat** (aucun thread ni calcul, colonnes marquées éclairées en ciel ouvert dès leur arrivée, captures comprises) ; appliqué à chaud (passage au complet : lumière effacée puis recalculée, anciens maillages gardés en attendant). Complet dans tous les préréglages, très bas compris : le plat éclaire grottes et nuit, ce qui change le jeu plus qu'un réglage de qualité.
- **Limite connue** : une colonne déchargée laisse chez ses voisines la lumière qu'elle leur donnait, jusqu'à leur propre déchargement (bord de la distance de vue, invisible en pratique).
- **Alternatives écartées** : stockage séparé ciel/bloc (deux tableaux de 2 Kio, deux accès) ; propagation sur les threads de maillage par travaux indépendants (frontières de colonnes à recoller) ; copie complète des blocs dans le thread (mémoire doublée).

## D046 — Rendu de la lumière : lissage par sommet, courbe en uniforme, maillage après la lumière (v0.2, jalon 6)

- **Sommet** (toujours 8 octets) : second mot `layer:16 drop:4 animation:2 libre:2 bloc:4 ciel:4` (l'octet `PackedLight` tel quel). Ciel et bloc restent séparés pour que la nuit (jalon 7) ne baisse que le ciel.
- **Lissage** (`mesher/shading.rs`, façon Minecraft) : chaque coin moyenne, canal par canal (arrondi au plus proche), la cellule devant la face et les trois cellules du côté de la face autour du coin ; les cellules opaques sont ignorées, et la cellule de coin aussi quand les deux côtés sont opaques (la lumière ne passe pas en diagonale). Les 3 × 3 cellules autour de la cellule de devant sont lues une fois (opacité + lumière) et partagées par l'AO et la lumière ; si toutes les cellules claires ont la lumière de devant (air libre, roche), aucun calcul. Réglage `smooth_lighting` (coupé en très bas) : sans lui, la face prend la lumière de la cellule de devant. Liquides : même lissage, sans AO. Plantes et torches (croix) : lumière de leur propre cellule.
- **Fusion gloutonne** : la clé de fusion porte la lumière des 4 coins (12 octets au lieu de 6) ; deux faces de lumières différentes ne fusionnent pas. La diagonale du quad est choisie sur l'AO puis la lumière.
- **Shader** (`light.wgsl`, ajouté à `block.wgsl` et `model.wgsl`) : niveau = `max(ciel × facteur, bloc)` ; courbe de Minecraft `l / (4 − 3l)` tirée vers `1 − (1 − x)⁴` par le réglage **luminosité** (0-100 %, 50 par défaut, identique dans tous les préréglages et sans effet sur « personnalisé ») ; plancher d'ambiance 0,2 (rien n'est jamais tout noir) ; résultat en valeur d'affichage converti en linéaire (`^2,2`, les cibles sont sRGB) ; plein jour = couleurs inchangées. Teinte chaude `(1, 0,8, 0,56)` là où la lumière des blocs dépasse celle du ciel. Uniforme caméra : `light = (facteur du ciel, luminosité, plancher)` ; `Renderer::sky_light` (1 pour l'instant) servira à la nuit sans remailler.
- **Ordonnancement** : une section n'est maillée qu'une fois **sa colonne et ses 8 voisines éclairées** (la bordure lissée lit la lumière des voisines) ; le thread de lumière renvoie à chaque lot les colonnes éclairées pour la première fois (`LightResult::lit`) et les sections signalées par le moteur ; une colonne qui devient « éclairée avec ses voisines » est maillée en entier, sinon seules les sections signalées (lumière ou bordure changée) sont remaillées. Plus de double maillage au chargement ; la bordure de chargement perd un anneau de colonnes maillées (il faut 5 × 5 colonnes chargées). Un changement de bloc remaille tout de suite les sections voisines (réactivité) avec une **lumière provisoire** de la case changée (`ClientWorld::guess_light` : le maximum de ses voisines éclairées atténué, et sa propre émission, sans jamais assombrir), la lumière exacte suit quelques millisecondes après. `is_settled` (bancs) attend aussi que le thread de lumière soit à jour (`LightWorker::is_idle`, compte des travaux envoyés).
- **Captures** : `render_image` éclaire tout le monde chargé avant de mailler (`ClientWorld::compute_light`, résultat indépendant de l'ordre). Scène `light` (grotte fermée éclairée par une torche à cheval sur deux colonnes, tunnel sans lumière, prairie) ; `caves-42` refaite (grotte sans lumière : sombre). `ravine-42` non refaite (paramètres de capture perdus ; ravin au jour, peu changé).
- **Modèles** (bateaux) : lumière de la cellule à 0,5 bloc au-dessus de leur position (au-dessus de l'eau), attribut par sommet, même courbe.
- **Torches et végétation** : une croix qui émet de la lumière n'est jamais retirée par le réglage végétation (réduite ou coupée).
- **Coût** (cloud, même machine, avant → après) : section de surface 0,21 → 0,21 ms, damier (pire cas) 0,97 → 1,44 ms (+49 % : toutes les faces isolées, lumière variable), eau qui coule 0,24 → 0,31 ms. Banc lu avec lumière réelle (`with_light`). Réglage « éclairage lissé » pour réduire.
- **Alternatives écartées** : remailler à chaque arrivée de lumière (double maillage) ; sommet de 12 octets ; lumière par face seulement (paliers visibles) ; une texture de lumière 3D échantillonnée par le shader (mémoire GPU et mise à jour par section).

## D047 — Jour, nuit et ciel : cycle dans `core`, heure du serveur interpolée, ciel en passe plein écran (v0.2, jalon 7)

- **Cycle** (`core::sky::DayCycle`, pur et testé) : `day` de `dimensions/<nom>.ron` (`length` 24 000 ticks = 20 min, `day_share` 0,5 — paramètre que les saisons moduleront en v0.5 —, `twilight` 0,06 du cycle par lever/coucher, `night_light` 0,2), tout borné (1 min à 10 h, part du jour 5-95 %, crépuscule ≤ la plus courte des deux parts). Le temps 0 est le premier lever. **Facteur du ciel** = `night_light + (1 − night_light) × smoothstep` d'une marge signée continue (distance au lever ou au coucher le plus proche, positive le jour) : continu sur tout le cycle, quelle que soit la part du jour (testé tick par tick, dans `[night_light, 1]`). Soleil : un demi-tour pendant le jour, un demi-tour pendant la nuit, quel que soit leur rapport ; lever à l'est (+X), chemin penché vers le sud (`path_tilt`). **Lune** : 8 phases, une par jour (nuit comprise), 0 = pleine.
- **Heure du monde** : `world.ron.day_time` compte désormais les ticks **depuis le premier lever** (sans modulo : les jours se comptent pour les phases) ; anciens mondes compatibles (valeur < 24 000). Option de monde `day_cycle` (création : bouton « Cycle jour/nuit » ; commande `/daycycle on|off|query`), `#[serde(default = true)]`. L'heure avance à chaque tick joué (donc gelée en pause). `/time set` avance jusqu'au **prochain** moment demandé (jamais de retour en arrière, les phases continuent), `day`/`night` juste après le lever/coucher (moitié du crépuscule), `noon`, `midnight` ou ticks ; `/time add` ajoute (saturé) ; la réponse donne l'heure du jour, la durée et le numéro du jour.
- **Protocole** (version 4) : `ServerMessage::DayTime { time, cycle }` à l'arrivée, tous les 20 ticks (`DAY_TIME_PERIOD`) et après chaque commande ; `NewWorld.day_cycle`.
- **Client** : `DayClock` avance au rythme de 20 ticks/s entre les messages, rattrape l'écart en accélérant (au plus ×2) ou en ralentissant (jusqu'à l'arrêt) : **jamais de recul** ; il ne dépasse pas le dernier message de plus de 1,5 période, donc s'arrête tout seul quand le serveur s'arrête (pause) ; un écart de plus de 200 ticks (`/time`) est rejoint d'un coup. Écran titre : terrain au moment `day` (lumière pleine, lueur du matin).
- **Ciel** (`skies/<dimension>.ron`, chargé depuis les packs **et** les packs de ressources) : dégradés zénith/horizon de jour, de nuit et de crépuscule, textures `sun`/`moon` (sprites 16 × 16 du pack, rampes `sun` et `moon` de la palette), tailles, inclinaison du chemin, étoiles (densité, éclat, scintillement), bornés. Sans fichier : bleu uni, sans astres. `SkyFrame` (client, pur) mélange en linéaire nuit → jour selon la lumière du jour, tire le zénith vers le crépuscule et calcule la lueur. **Passe plein écran** (`sky.wgsl`, un triangle) dessinée en premier dans la passe du monde, sans profondeur, avec les groupes caméra/textures des blocs : direction de vue par l'inverse de la vue-projection relative à la caméra ; lueur orangée près de l'horizon côté soleil ; étoiles procédurales (cellules d'un cube tournant avec le chemin du soleil, ~2 pixels, hachage entier, scintillement par sinus) qui s'effacent près de l'horizon et au jour (`(1 − jour)²`) ; soleil et lune lus texel par texel (`textureLoad`, pixel art net), droits à l'écran ; phase de la lune ombrée par texel (terminateur elliptique). Pas de ciel avec les yeux dans un liquide (son brouillard le cache). Le **brouillard** et la couleur d'effacement prennent l'horizon du moment (un peu de lueur au crépuscule). Facteur du ciel dans l'uniforme existant : la nuit tombe **sans remailler**.
- **Réglage** `stars` (graphismes, coupé en « très bas », coût presque nul). Captures : `--time <tick>` (midi par défaut ; aussi l'heure de départ d'un monde temporaire `--seed`).
- **Relecture** : la lune change de phase **à midi** (sous l'horizon ; testé : jamais tant qu'elle est au-dessus de −0,12). Le serveur envoie son cycle borné (`DayState { time, flows, cycle }`) dans `Welcome` (protocole 5) : le client n'utilise plus ses propres packs pour le cycle (seules les captures hors ligne le lisent localement) et a l'heure avant la première image du monde ; `/time` relit le cycle de la dimension du joueur. Le ciel est dessiné **après les opaques**, sur le plan lointain (`GreaterEqual` en reverse-Z, sans écriture) : seuls les pixels vides sont calculés. Les étoiles scintillent sur un temps enroulé sur 2π avec des vitesses entières (pas de saut). L'horloge du client s'arrête en pause.
- **Alternatives écartées** : heure dans chaque `Tick` (message par tick plus lourd sans besoin) ; sphère de ciel maillée (plus de géométrie, même rendu) ; 8 textures de phases (le pack n'a qu'une lune à dessiner) ; lumière de la nuit par remaillage (coût de tout le monde chargé à chaque palier).

## D048 — Nuages : grille d'instances façonnée dans le shader, motif périodique, deux passes (v0.2, jalon 7)

- **Pack** : `clouds` (optionnel) de `skies/<dimension>.ron` : hauteur du dessous (Terra : 300, au-dessus des collines, sous les grands pics), épaisseur (4), taille de cellule (12), **couverture** 0-1 (0,45 ; la météo de la v0.5 la modulera), opacité, vitesse (blocs/s) et direction (degrés), couleurs jour / crépuscule / nuit. Tout borné (`core::sky::Clouds`, testé). Sans `clouds` : pas de nuages.
- **Dérive déterministe** : décalage = vitesse × temps du monde (ticks, interpolé) ; même heure, même ciel (captures `--time`, rechargement). Le temps gelé en pause gèle les nuages.
- **Sans maillage** : une instance par cellule d'une grille qui suit la caméra (portée = 2 × distance du brouillard, bornée à 256-512 blocs) ; le vertex shader tire la couverture d'un bruit de valeur à deux échelles (nœuds tous les 16 et 4 cellules) évalué **par cellule** (carrés pixel art) et réduit à rien les cellules vides et les faces latérales collées à une cellule nuageuse. Le motif se répète toutes les 256 cellules : la position de la caméra dans le motif est calculée en `f64` puis ramenée à une période, donc précise et sans tremblement partout dans le monde. Aucun travail CPU par image hormis un uniforme de 64 octets.
- **Réglage `clouds`** : désactivés / **simples** (une face plate par cellule : 6 sommets) / **complets** (boîtes à dessus, dessous et côtés ombrés : 36 sommets). Préréglages : très bas désactivés, bas et DS simples, moyen à ultra complets. Application à chaud (lu dans `RenderOptions` à chaque image). Volume choisi plutôt que deux couches : silhouette « à la Minecraft », même coût de géométrie à peu près, et un seul motif à régler.
- **Deux passes en mode complet** (profondeur seule, puis couleur en `Equal`, position `@invariant`) : les nuages translucides ne s'empilent pas (une seule surface par pixel), et le relief qui dépasse les cache correctement. En mode simple, une seule passe (couleur + écriture de profondeur) : une couche plate ne se recouvre pas. Dessinés après les blocs opaques, avant l'eau. Couleur : nuit → jour selon la lumière du jour, puis vers la teinte du crépuscule ; fondus vers la couleur du brouillard au-delà de 45 % de la portée, transparents au bord.
- **Coût connu** : la couverture (`cloudy()`, deux bruits de valeur) est recalculée par sommet, et jusqu'à 5 fois en mode complet (cellule + 4 voisines) ; négligeable aujourd'hui, à mettre en texture (une valeur par cellule) si une mesure le montre.
- **Alternatives écartées** : maillage CPU remaillé par la dérive (coût par image) ; lancer de rayons plein écran (coûteux en pixels sur le DS, profondeur plus délicate) ; deux couches plates (moins lisible en volume).

## D049 — Feu : règle des mises à jour planifiées, âge hors du monde, hasard haché (v0.2, jalon 8)

- **Pack** : champ `flammability: (catch, burn)` d'un bloc (échelle de Minecraft : `catch` = facilité avec laquelle l'air voisin s'enflamme, `burn` = facilité avec laquelle le bloc lui-même prend et se consume). Bûches (5, 5), planches (5, 20), feuilles (30, 60), herbes, fougères, buissons, fleurs (60, 100), liane (15, 100). Le bloc `strata:fire` porte `fire: (tick_rate: 30, max_age: 15)` : sans objet, sans collision, remplaçable, lumière 15, rendu en croix (texture fixe ; l'animation vient avec les textures animées). Un liquide `puts_out_fire: true` (l'eau) l'éteint.
- **Simulation** (`core::updates::fire`) dans la même file de blocs actifs que les liquides, avec le **même budget par tick** (`fluids.updates_per_tick`), où **un pas de feu compte pour trois** (`FIRE_UPDATE_COST` : banc `fire/prairie_fire_40_ticks`, 6 988 pas de feu en 35,8 ms soit ~5,1 µs le pas, contre 3 478 pas de liquide en 6,3 ms soit ~1,8 µs pour `fluids/large_flow_settles` ; la boîte d'air de 53 cases lue à chaque pas domine). Au budget par défaut (2 048), un incendie ne prend donc pas plus de ~3,5 ms par tick ; `fluids.flow: false` ne fige plus que les liquides (les entrées de liquide sont oubliées au moment où elles sortent de la file). Règles proches de Minecraft : pas tous les 30 + 0-9 ticks ; l'âge croît de 0 ou 1 ; le feu tient sur un bloc solide ou contre un bloc inflammable, jamais contre un liquide qui l'éteint ni sous la pluie ; sans combustible voisin, il meurt au-delà de l'âge 3 ; à l'âge maximal, 1 chance sur 4 de mourir sauf s'il brûle sur un combustible encore destructible ; chaque voisin inflammable prend avec `burn / 300` (côtés) ou `/ 250` (dessus, dessous) et devient air ou parfois une nouvelle flamme ; l'air de la boîte 3 × 6 × 3 (jusqu'à 4 au-dessus) qui touche un bloc inflammable s'allume avec `(catch + 54) / (âge + 30)` sur 100 (plus rare en hauteur). Un feu à son âge maximal **ne se propage plus** : les âges ne font que croître le long d'une chaîne de feux, donc tout incendie s'éteint (test : forêt de 9 × 9 brûlée puis éteinte, aucun bloc actif). Voisinage : un feu qui perd son support ou touche de l'eau s'éteint aussitôt (même mécanisme que les plantes sans sol).
- **Âge hors du monde** : table `position → âge` dans `BlockUpdates` (pas de variantes de bloc comme les liquides : 16 variantes pour une donnée éphémère, sans intérêt pour la sauvegarde). Retirée quand le bloc change ou que son entrée sort de la file sans feu. Comme les ticks planifiés (D042), ni l'âge ni le pas prévu ne sont sauvegardés ; mais **au chargement d'une colonne** (générée ou lue), `BlockUpdates::wake_fires` replanifie ses feux à l'âge 0 (seules les sections dont la palette contient un feu sont parcourues) : un feu rechargé ne reste jamais figé (test serveur).
- **Hasard déterministe** : splitmix64 amorcé par un hachage de (graine du monde mêlée à la dimension par FNV-1a, position, tick, sel) ; deux sels distincts pour le délai du pas et pour les chances du pas, qui sinon tiraient les mêmes nombres. Même ordre de file → même incendie. Tests : deux exécutions identiques à budget égal (2048 et 2) ; incendie de forêt figé sur une valeur de référence (nombre de changements et empreinte) ; autre graine ou autre dimension → autre incendie.
- **Valeurs dans le pack** : toutes les constantes du feu (délai, écart, âges, chances, zone d'allumage 3 × 6 × 3) sont des champs de `FireDef` (défauts de Minecraft, bornes dans `clamped()`, zone limitée à 7 × 7 × 12), écrits en entier dans `blocks/fire.ron` et reportés dans `docs/regles/equilibrage.md`.
- **Options de monde** : `fire: (spread, destroy)` dans `world.ron` (défaut `true`, `true`), boutons « Feu » et « Brûle » à la création (`NewWorld::fire_spread`, `fire_destroy` ; protocole version 6), commande `/fire spread|destroy on|off`, `/fire query`. `spread: false` : aucun nouveau feu (le voisin qui prend est seulement consumé) ; `destroy: false` : rien n'est consumé, le feu meurt tout de même à l'âge maximal.
- **Pluie (v0.5)** : point d'entrée `BlockAccess::rains_on(pos)` (faux par défaut), déjà consulté pour l'existence et l'allumage d'un feu ; testé avec un monde où il pleut partout.
- **Briquet** : objet `flint_and_steel`, `action: Ignite("strata:fire")`, catégorie Outils, créatif seulement (comme les seaux) ; le serveur vise la même case qu'une pose de bloc, exige de l'air ou une plante, et que le feu puisse y tenir.
- **Hors périmètre** : dégâts au joueur (pas de vie avant la v0.3). **Lave qui allume** les blocs inflammables proches : non fait, la lave immobile n'est jamais planifiée ; à faire avec les ticks aléatoires (croissance des plantes, v0.3+).

## D050 — Textures vivantes : images supplémentaires après les premières, animation et variantes dans le shader, raccords au maillage (v0.2, jalon 8)

- **Format** (`core::texture::multi`, guide : `docs/guide-textures.md`) : trois recettes de plus. `Animated(frames, frame_time)` ; `Random(variants, weights)` ; `Connected(base, connect: Edges | Vertical, border)`. Les images viennent de `Frames` : `List`, `Reseed` (même recette, autre graine ; l'image 0 garde la graine d'origine, donc les minerais posés sur la pierre ne changent pas), `Scroll`, `Sway`. PNG : bande verticale d'images carrées = animation ; une bande qui remplace une texture animée hérite de son `frame_time`. Bornes : 64 images, `frame_time` 1-255, poids 1-64, bordure ≤ 4. Pas d'imbrication (une base nommée fournit sa première image).
- **Couches** : `TextureLibrary.images` garde **une couche par texture nommée** (son `TextureId` ne change pas : blocs, icônes, wiki, ciel inchangés) ; les autres images vont dans `extra`, après toutes les premières (`layers()`, `image_layer(texture, i)`). `layouts[TextureId]` dit comment les utiliser. Raison : pas d'identifiants synthétiques pour les images, et le reste du moteur continue d'adresser une texture par sa couche.
- **Animation dans le shader** : tampon de stockage (groupe 1, liaison 2, étage vertex) d'un `u32` par couche, `première_extra:16 images:8 frame_time:8` ; le shader choisit `(ticks / frame_time) % images` (miroir CPU : `TextureLayout::frame_at`, testé). Aucun remaillage ni envoi par image. Le format de sommet ne change pas (couche 16 bits, `animation:2` reste le code de défilement des liquides de D043) : on **garde le défilement** de l'eau et de la lave (il montre le sens du courant) et on y ajoute l'ondulation par images (`Sway`).
- **Variantes aléatoires dans le shader de fragments** (relecture du jalon) : choisies au maillage, elles entraient dans la clé de face et cassaient la fusion gloutonne. Le mailleur garde maintenant la couche de base ; le fragment retrouve son bloc (`floor(position locale interpolée − normale × 0,5)` + origine de la section, entière, passée en *immediates* avec le décalage caméra : 32 octets au lieu de 16) et tire la variante par `position_hash` (même code qu'en Rust) et une table de stockage (groupe 1, liaison 3, étage fragment) : par couche, la couche de la deuxième image et `début:24 images:8` vers les **cumuls précalculés** des poids. Miroir CPU testé contre `TextureLayout::random_index` sur toutes les textures aléatoires du jeu ; captures identiques à l'ancienne version à 12 pixels près. Les plans de plantes ne prennent pas de variante (comme avant). **Sommets** d'une section de surface vallonnée en pierre à 3 variantes (test `random_variants_add_no_vertex_to_a_surface_section`) : lumière lissée 2 012 → 1 816 (= sans variantes), lumière plate 1 732 → 1 164 (−33 %). `random_index` reste le miroir CPU (tests), pas un chemin chaud.
- **Raccords au maillage** (`client::mesher::variants`) : la couche choisie remplace celle du bloc dans la clé de face (un raccord dépend des voisins, pas seulement de la position). `MeshBlock.varied` (textures connectées seulement) évite tout coût aux autres blocs. Raccord `Edges` : côtés pris dans le repère de texture de la face (`right`, `down`), voisin identique dont la face n'est pas cachée par un bloc identique ; `Vertical` : faces de côté seulement. Les blocs couchés (bûches) ne sont pas raccordés (repère tourné).
- **Hachage de position** : `content::position_hash` (multiplications et mélanges 32 bits, recopié dans `block.wgsl`), coordonnées du monde : même variante quelle que soit la section ou la machine.
- **Réglages** : `liquid_animation` devient `animated_textures` « Textures animées » (alias serde pour les anciens fichiers ; coupé en très bas, coût nul : uniforme ; le shader ne lit plus la table d'animation quand il est coupé) ; nouveau `texture_variants` « Variantes de textures » : variantes aléatoires par l'uniforme `effects.w` (coût nul), raccords au maillage (remaille) ; coupé en très bas.
- **Formats refusés** : `Frames::List` qui cite une texture de plusieurs images est une erreur de pack (elle ajoutait silencieusement toutes ses images).
- **Limite de couches** : la carte demande maintenant `max_texture_array_layers` de l'adaptateur (Vulkan garantit 256, 2 048 en général) ; le jeu de base doit tenir dans 256 (test).
- **Coût** (banc de maillage avec herbe, terre, pierre à 3 variantes, VM partagée, avant le passage au shader) : surface 0,28 ms, damier 2,05 ms ; sans variantes : 0,30 ms et 1,90 ms. Depuis, les variantes ne coûtent plus de faces ; le shader fait au plus 64 tours de boucle par pixel des seules couches aléatoires (3 en pratique).
- **Portail d'essai** `strata:portal` : translucide, sans collision, lumière 11, animé ; décoratif (vrais portails en v0.10). `Block::hit_box` vise désormais tout cube non liquide, même sans collision, pour pouvoir le casser. **Bibliothèque** `strata:bookshelf` : planches dessus et dessous, côtés connectés verticalement, inflammable.


## D051 — Atmosphère : biomes envoyés avec les colonnes, teintes au maillage, brouillard du biome (v0.2, jalon 9)

- **Biomes côté client** : le serveur envoie avec chaque colonne sa carte des biomes 16 × 16 (`core::chunk::BiomeMap`, `BiomeId` = rang du biome dans la liste triée par identifiant de `WorldgenContent::biomes`) dans `ServerMessage::Column { column, biomes }`, et la liste des biomes (`BiomeInfo`) dans `Welcome` (protocole 7). Le client ne fait que l'afficher (F3 : « Biome : … »). 16 × 16 plutôt que 4 × 4 : les frontières suivent exactement celles du terrain généré (herbe, sable) ; 256 octets par colonne sur le fil (postcard, entiers variables).
- **Sauvegarde : recalculée depuis la graine**, jamais stockée. Les biomes sont une fonction pure de la graine et de la position (rien ne les modifie en v0.2), et un rang numérique stocké deviendrait faux dès qu'un pack ajoute un biome. Le calcul (`Generator::biome_map`, 218 µs par colonne, banc `biome_map_column`) est fait par les **threads de génération** (`Job::Biomes`), pas par le tick : une colonne lue d'une région n'est envoyée qu'avec ses biomes (test `saved_columns_come_back_with_their_generated_biomes`). Si les biomes deviennent modifiables (v1.x), on stockera une palette d'identifiants texte par colonne.
- **Teintes** (`core::content::tint`) : chaque biome porte `colors: (grass, foliage, water, fog)`, des **facteurs** par canal en espace d'affichage (1 = couleur peinte, bornés à 0-2, transmis en `Tint` 8 bits où 128 = ×1) ; un bloc porte `tint: (kind: Grass|Foliage|Water, faces: All|TopFringe)`. Herbe (`TopFringe` : dessus teinté, côtés teintés seulement sur la frange, dessous jamais), herbes hautes, fougères, buissons (`Grass`) ; feuilles de chêne, de jungle, d'acacia, lianes (`Foliage`) ; eau (`Water`). Bouleau et sapin gardent leur couleur propre. **Facteurs plutôt que textures neutres** : les plaines (facteur 1) restent exactement comme avant, les icônes, le wiki et la planche de textures gardent leurs couleurs sans teinte par défaut à appliquer, et les rampes gardent leurs nuances (une texture grise teintée perd la variation de teinte de la rampe). Limite : un facteur ne peut pas changer une couleur au-delà de ×2 par canal (largement assez pour savane, marais, taïga).
- **Frange des côtés** : une recette `Overlay` marque les pixels de sa base restés visibles avec l'alpha `UNTINTED_ALPHA` (254), invisible ailleurs (icônes, wiki, test d'alpha à 0,5) ; sur une face masquée, le shader teinte selon `clamp(a × 255 − 254, 0, 1)`, que les mipmaps mélangent proprement. Un pack de ressources en PNG fait de même (guide des textures). Rejeté : un second quad de frange (z-fighting, faces en plus), une couche de masque par texture.
- **Mélange au maillage** : `ColumnTints` (client) calcule par colonne, pour chaque sorte, la couleur de chacun des 17 × 17 coins : moyenne des 2r × 2r blocs qui touchent le coin (tables de sommes, 8,4 µs par colonne à r = 3, mise en cache par colonne et par rayon, partagée par ses sections via `Arc`). Un coin ne dépend que de sa position dans le monde : **aucune cassure** aux frontières de colonnes (test sur deux colonnes maillées). Rayon 0 : une couleur par bloc (frontières nettes). Le rayon est borné à 8 (les 8 colonnes voisines suffisent). Réglage `biome_blend` « Mélange des biomes » : très bas 0, bas et DS 1, moyen 2, haut 3, ultra 4 ; changer la valeur remaille.
- **Fusion gloutonne** : la clé de face (12 → 16 octets) porte la couleur quand les 4 coins sont égaux ; sinon la face est seule (quad 1 × 1, couleurs par coin). Loin des frontières tout fusionne comme avant (test).
- **Sommet 8 → 12 octets** : troisième mot `r:8 g:8 b:8 masqué:1`. Mesure (captures, tout le monde chargé) : graine 42, préréglage haut, 6,78 M sommets : sommets 54 → 81 Mo, avec les indices 95 → 122 Mo (+29 %) ; DS, 1,88 M sommets : 26 → 34 Mo (+7,5 Mo, très loin des 2 Go). Rejeté : palette de couleurs par section adressée par des bits volés à la couche (2 bits libres seulement, table par section à gérer) ; texture de couleurs autour de la caméra lue par le shader (pas calculé au maillage, mise à jour à chaque déplacement).
- **Coût de maillage** (VM partagée) : section de surface avec herbe teintée 0,265 ms, la même à cheval sur une frontière 0,28 ms, damier 2,11 ms, eau qui coule 0,38 ms.
- **Distance demandée et brouillard** (relecture) : une section n'est maillée qu'avec ses 5 × 5 colonnes chargées et éclairées (D046), donc les deux derniers anneaux du disque chargé ne sont jamais dessinés (`world::UNDRAWN_RING` = 2). Le client demande au serveur `distance de rendu + 2` colonnes (`world::requested_view_distance`, borne du protocole portée à 40) : la distance affichée dans les options est celle qui est dessinée. Le brouillard se termine à `(distance dessinée − 2) × 16` blocs (`JAGGED_EDGE` : le disque dessiné est crénelé en diagonale et la caméra peut être n'importe où dans sa colonne) ; un test reconstruit le disque du serveur (`protocol::in_view_disc`, partagé avec le chargeur) et les règles d'éclairage et de maillage du client, et vérifie que le brouillard est complet avant la première colonne non dessinée vue de plusieurs points de la colonne de la caméra (distances 2 à 32). Mesure DS (`--bench-scene flyover --preset ds`, xvfb, cloud) : pic RSS 218 → 234 Mio, démarrage jusqu'au monde chargé ~7,7 → ~12,3 s (disque de 8 au lieu de 6, ~1,8 × plus de colonnes) ; très loin des 2 Go, gardé. Début du brouillard à 60 % de la fin (inchangé).
- **Plus tard (v1.0)** : biomes envoyés en palette par colonne (moins d'octets quand une colonne n'a qu'un ou deux biomes), avec le protocole multijoueur.
- **Teinte du brouillard** : `colors.fog` multiplie l'horizon du ciel (donc l'heure : nuit sombre, lueur au crépuscule) ; moyenne linéaire des biomes chargés à ±24 blocs de la caméra (pas de 8), suivie en douceur (`sky::BiomeFog`, ~1,5 s pour les deux tiers du chemin ; captures : sans lissage). L'horizon **du ciel** prend la même teinte que le brouillard (`SkyFrame::with_fog_tint`) : le terrain noyé et le ciel derrière lui restent d'une seule couleur, ainsi que la couleur d'effacement et le fondu des nuages.
- **Nuit** (remplace les valeurs de D046/D047) : `night_light` 0,2 → 0,1 (`terra.ron` et défaut), plancher d'ambiance 0,2 → 0,15, et le relèvement de la courbe par le réglage de luminosité croît comme le **carré** du réglage (50 % → un quart du relèvement, 100 % inchangé). Herbe de nuit loin des feux (`fire-night`) −25 %, terrain au clair de lune nettement plus sombre mais lisible ; plein jour inchangé.
- **Nuit, réglage final** (clôture v0.2, remplace la ligne précédente pour `night_light`) : 0,1 rendait falaises et terrain illisibles au clair de lune (captures `cliff-night-42`, `sky-night`). `night_light` **0,4** (`terra.ron` et défaut), plancher d'ambiance 0,15 et relèvement au carré gardés : au réglage par défaut (50 %), valeur perçue ≈ 0,43 la nuit contre 1 le jour et 0,15 au fond d'une grotte (≈ 6,5 × plus sombre que le jour en linéaire). La lumière du ciel prend la nuit une teinte froide `MOON_LIGHT` (0,78 ; 0,88 ; 1,15) proportionnelle à `(1 − facteur du ciel) × ciel × (1 − chaleur)` : rien sous terre ni près d'une torche, dont la lumière chaude ressort d'autant mieux. Relief et silhouettes lisibles, pas le détail fin.
- **Brouillard sous terre** (clôture v0.2) : le brouillard prenait la couleur du ciel partout ; dans une caverne, au-delà de la distance dessinée (DS : ~64 blocs), on voyait des taches bleu-blanc. Sa couleur, celle de l'horizon et du zénith (le ciel vu au-delà du monde dessiné) suivent maintenant la **lumière du ciel aux yeux** : ouverture = (niveau / 15)², 0 → `cave_fog` du ciel (`skies/terra.ron`, `#0c0c12`, défaut identique si absent), 1 → ciel inchangé ; lueur du crépuscule, étoiles et nuages s'effacent avec elle, soleil, lune et lumière du monde intacts (`SkyFrame::under_ground`). Lissée comme la teinte de biome (`sky::CaveFog`, même constante de 1,5 s ; captures : sans lissage). Au carré pour qu'une entrée de grotte assombrisse déjà un peu. Rien ne change en surface (ouverture 1, captures identiques à l'octet) ni sous l'eau ou dans la lave (le brouillard du liquide remplace celui du ciel).

## D052 — Particules : système client à pool borné, définitions en pack, un seul appel de dessin (v0.2, jalon 9)

- **Côté client uniquement** (`client::particles`) : le serveur n'en sait rien et aucune donnée de monde n'est créée ; le client les déduit de ce qu'il reçoit déjà. Une casse est un `BlockChanged` où l'ancien bloc (pas un liquide) laisse place à de l'air, un bloc remplaçable ou un liquide (`ParticleTable::breaking`) : casse par le joueur, feu, plante emportée par l'eau. Poser un bloc, un liquide qui se retire ou un bloc identique ne donne rien. En multijoueur (v1.0), chacun verra les casses des autres sans message de plus.
- **Pack** : `particles/<nom>.ron` (`core::content::ParticleDef` : `texture` absente = un morceau 4 × 4 pixels de la texture du bloc émetteur, `color`, `lifetime`, `size`, `gravity` (négative : monte), `speed`, `drag`, `hang` (goutte qui grossit avant de tomber), `collides`, `glows`, `in_liquid`, `burst`, `chance`, `impact` (particules lancées à l'atterrissage ou en tombant dans un liquide)). Les blocs portent `particles: (breaking, drip, ambient)`. Aucun identifiant de particule n'est connu du moteur : une particule se **déclare défaut** avec `default_for: Some(Breaking)` (une par sorte ; le pack de plus haute priorité gagne, deux dans un même pack sont une erreur de pack) ; un bloc sans `breaking` prend ce défaut (aucun si aucun pack n'en déclare), `breaking: None` le retire (feu, liquides), `breaking: Some("…")` en choisit un autre. `drip` : goutte sous le bloc plein situé sous ce bloc (eau, lave, y compris en écoulement) ; `ambient` : particule dans le bloc au-dessus d'un bloc plein (bulles d'eau). Les particules sont chargées avec les packs de ressources (apparence), `remove.ron` accepte `particles`.
- **Teinte** : les éclats d'un bloc teinté prennent la couleur du biome de sa colonne (non mélangée, suffisant pour des morceaux de quelques pixels) quand la face tirée au hasard est teinte (dessus seulement pour `TopFringe`).
- **Pool borné alloué une fois** (`Pool`, `Vec::with_capacity`) : plein, il refuse les nouvelles particules au lieu de grandir ; retrait par échange avec la dernière (`swap_remove`) ; les instances GPU sont réécrites chaque image dans un `Vec` gardé d'une image à l'autre, le tampon GPU ne grandit qu'en doublant jusqu'à la capacité. Aucune allocation par image après le démarrage (tests). Taille selon le réglage : complètes 4 096, réduites 1 024 (rafales ÷ 4, échantillonnage ÷ 3), désactivées 0 (rien n'est calculé ni dessiné). Changer de réglage ne réalloue que si la taille change.
- **Physique** : point au bas du carré, gravité, frottement de l'air (`drag^dt`), arrêt axe par axe sur les blocs `solid` (sous-pas de 0,4 bloc au plus, pas de traversée), frottement au sol. Rejeté : boîte de collision par particule (inutile à cette taille), physique partagée du joueur (trop chère pour des milliers de points).
- **Émetteurs autour de la caméra** : un budget de cellules tirées au hasard par seconde (2 400 complètes, 800 réduites, 96 au plus par image, report fractionnaire d'une image à l'autre) dans ±12 blocs à l'horizontale et ±8 à la verticale ; chaque cellule coûte 2 à 4 lectures de blocs. Indépendant de la fréquence d'images.
- **Rendu** (`render::particle_pipeline`, `particle.wgsl`) : un carré face à la caméra par instance (bande de 4 sommets, vecteurs droite/haut en immédiats), un seul `draw` instancié dans la passe opaque après les modèles et avant le ciel ; texture du tableau des blocs, transparence par seuil (pas de tri), lumière de la cellule du bas de la particule (ciel × facteur du ciel et blocs, courbe partagée `light.wgsl` ; `glows` = lumière de bloc pleine) et brouillard comme les blocs. Les particules rapetissent dans le dernier quart de leur vie.
- **Captures** : `--break x,y,z` casse un bloc juste avant la capture, `--particles <secondes>` simule les particules (pas de 1/60 s) ; scène `particles` (surplomb sous un bassin d'eau et de lave, tas de blocs) ; captures `particles-break-*` et `particles-drips-*`.
- **Coût** (VM partagée, `particles/frame_2000`) : déplacer 2 000 particules et écrire leurs instances, 0,41 ms par image (~0,2 µs la particule, surtout des lectures de blocs dans la table de colonnes) ; le profil DS (réduites) en a au plus 1 024. Piste si besoin : mettre en cache la colonne de la dernière lecture.


## D053 — Audio : `rodio` pour la sortie, mixeur maison, sons synthétisés depuis des recettes du pack (v0.2, jalon 10)

- **Crate de lecture : `rodio` 0.23** (RustAudio, maintenue, MIT/Apache-2.0), sans ses fonctions par défaut : `playback` (sortie via `cpal` → ALSA sous Linux, WASAPI sous Windows) et `vorbis` (décodage Ogg Vorbis via `symphonia`, pur Rust). Préférée à `kira` : API plus petite et stable, et le jeu n'utilise de `rodio` que deux choses (ouvrir la sortie, décoder un `.ogg`) ; le mixage, la spatialisation et les volumes sont faits par le jeu, donc testables sans périphérique. Dépendance système : `libasound2` (déjà dans `install-linux-deps.sh`, la CI et `installation-ds.md`).
- **Sans périphérique** (cloud, CI, DS sans carte) : `DeviceSinkBuilder::open_default_sink` échoue → une ligne `info` « no audio device: playing without sound », aucun son n'est rendu ni mixé ; les sous-titres et tout le reste fonctionnent. ALSA écrit quelques lignes sur la sortie d'erreur à cet essai (bibliothèque C, non filtrable).
- **Mixeur** (`client::audio::mixer`, pur) : une seule source `rodio` stéréo infinie demande au mixeur des blocs de 512 trames (~12 ms) et reçoit les commandes du jeu (jouer, fonds, musique, étouffement) par un canal borné entre deux blocs ; aucun verrou dans le fil audio. `Output::send` renvoie `false` si la file est pleine : l'appelant ne retient rien et redemande (fond, fondu, morceau) à l'image suivante. Les **contrôles** (auditeur, volumes, salle de réverbération, audio spatial) ne passent pas par la file : valeurs atomiques écrasées par le jeu (« dernier gagnant »), lues avant chaque bloc et appliquées seulement si elles changent. **Rien n'est libéré dans le fil audio** : tampons, blocs de musique et flux lâchés partent dans une poubelle bornée (1 024 places) que le fil principal vide à chaque image, et les blocs de musique joués reviennent au fil `music-read` (canal de recyclage borné) pour être remplis de nouveau ; tampon du départ de réverbération préalloué. Au plus **16 sons démarrés par image**, le même son à moins de 4 blocs d'un autre de la même image étant fondu avec lui (`/fill`, grosse casse). Gains par voix recalculés à chaque bloc et rampés (pas de clic quand l'auditeur tourne) ; lecture à vitesse variable par interpolation linéaire (hauteur, conversion 44,1 kHz → fréquence du périphérique). **32 voix** au plus : une nouvelle remplace la plus faible si elle est plus forte, sinon elle est ignorée.
- **Spatialisation** : gain en 1/distance (plein jusqu'à 1 bloc), fondu à zéro sur le dernier quart de la portée (`range` de la recette, 16 blocs par défaut) ; panoramique à puissance constante selon le côté (oreilles tournées par le lacet de la caméra, pas par le tangage), recentré à moins d'un bloc ; ×0,8 derrière (repère avant/arrière). Réverbération et occlusion : sous-tâche suivante.
- **Synthèse dans `core::audio`** (et non une crate dédiée) : les recettes sont du contenu de pack chargé avec le reste (`Content::sounds`), pur et déterministe, sans dépendance nouvelle ; `wikigen`/`balance` pourront les lire. Quatre couches (bruit coloré filtré avec enveloppe et rafales, grains, modes résonants, bulles), filtres biquad RBJ, générateur SplitMix64. Tampons mono 44,1 kHz normalisés à la crête `volume` (≤ 1), fin adoucie (5 ms), silence final retiré. Recettes **bornées au chargement** (durée ≤ 10 s, 16 variantes, 512 grains, 16 couches, fréquences 20 Hz–0,45 × 44,1 kHz…) avec une erreur de pack par valeur corrigée.
- **Variations** : chaque variante a sa graine (hachage FNV de l'identifiant ⊕ rang) ; une lecture tire une variante (jamais la précédente) et une vitesse dans `pitch`. Variantes rendues **à la première demande** sur un fil `sound-bank` (synthèse et décodage `.ogg` hors du fil principal ; un son pas encore prêt n'est pas joué, il le sera la fois suivante) puis gardées : ~10 Mo en f32 si toutes les variantes de la v0.2 ont été jouées (dont 3 Mo pour le vent).
- **Matériaux** (`sound_sets/*.ron`) référencés par le champ `sound` des blocs (existant depuis la v0.1) ; matériau inconnu = erreur de pack. Feuilles séparées de l'herbe (`strata:leaves`), eau, lave et feu ont le leur.
- **Déclenchement côté client** depuis ce qu'il reçoit déjà : changements de blocs (casse si le nouveau bloc cède la place — air, plante, liquide — et l'ancien n'est pas un liquide ; pose dans le cas inverse ; l'eau qui coule est muette), corps prédit du joueur (un pas tous les 1,6 bloc au sol selon le bloc sous les pieds, une brassée tous les 2,2 blocs dans un liquide, plouf en y entrant à plus de 2 blocs/s ; rien en vol ni en bateau, téléportation ignorée), blocs bruyants tirés au sort autour de l'auditeur (300 par seconde, ±12 blocs, 4 sons au plus par seconde). Le vent est prêt (recette `wind`, catégorie ambiance) pour les ambiances de la sous-tâche suivante.
- **Volumes** (`settings.sound`, onglet **Son**) : général × catégorie, courbe quadratique ; appliqués à chaud ; hors des préréglages.
- **Sous-titres** : clé de traduction dans la recette, ligne rafraîchie si le même son revient, 3 s après le dernier, 6 lignes au plus, direction ← → ↑ ↓ (glyphes ajoutés à la police pixel) par un message Fluent par direction ; widget `Log` du HUD (`subtitles`, déplaçable dans l'éditeur). Les pas et brassées du joueur ne sont pas sous-titrés.
- **Remplacement `.ogg`** : `sounds/<nom>.ogg` du pack le plus haut remplace la recette (sauf si un pack plus haut redonne une recette) ; décodé à la première demande (fil `sound-bank`), mélangé en mono, converti à 44,1 kHz, 60 s au plus ; illisible → avertissement et recette.
- **Outil** : `strata --render-sounds <dossier>` écrit toutes les variantes en WAV (guide : `docs/guide-sons.md`).

## D054 — Ambiances, réverbération du lieu, étouffement derrière les murs, réglage « Audio spatial » (v0.2, jalon 10)

- **Ambiances en pack** (`ambiences/<nom>.ron`, chargées dans `core::audio` avec les sons) : biomes nommés par identifiant (rapprochés côté client des `BiomeInfo` envoyés par le serveur, le client n'ayant pas le registre des biomes) ou `underground: true` ; **fonds en boucle** (`beds`) et **sons ponctuels** (`events`, sous-titrés, placés au hasard autour de l'auditeur, donc spatialisés et étouffés). 8 ambiances dans `strata` (plaines, forêt, jungle, marais, montagnes, mer, désert, sous terre), 6 fonds et 3 sons ponctuels nouveaux (`drip`, `frog`, `sand_gust` ; `wind` sert de rafale). Pas d'oiseaux : un cri synthétisé risque de ne pas être convaincant (repli CC0 à proposer si besoin).
- **Boucles** : `looped: true` dans une recette ; la dernière seconde (au plus un quart) est fondue à puissance constante dans le début, sans coupure de fin ni silence retiré ; une seule variante. Recettes de fond de 8 à 10 s (~3 Mo en f32 pour les 6), rendues au premier besoin sur le fil `sound-bank` (le fond est redemandé à chaque image tant qu'il n'est pas prêt).
- **Choix** : 25 échantillons de biome (pas de 8 blocs, ±16) → part de chaque ambiance (la mer s'entend de la plage, transitions spatiales douces) ; facteur souterrain = (peu de ciel à la tête : 12 → 6) × (sol plein au-dessus : 2 → 8 blocs) ; mis à jour 4 fois par seconde. Gains des fonds = volume × part × moment (lumière du jour) × altitude ; **fondu** côté jeu à 1/3 par seconde au plus, et rampe par bloc dans le mixeur (aucun saut). Le jeu ne démarre pas plus de 12 fonds (`MAX_BEDS`, un fond de plus attend qu'un autre soit lâché) ; le mixeur a 24 places (les fonds lâchés finissent leur bloc), centrés, en boucle, catégorie de leur recette (ambiance).
- **Densité acoustique** : champ `density` (0 à 1) du matériau (`sound_sets/*.ron`) ; sans lui, déduite du rendu (opaque plein 1 ; opaque non plein et translucide 0,6 ; liquide 0,4 ; découpé 0,2 ; croix et air 0).
- **Espace** : 26 rayons (faces, arêtes, coins) de 48 blocs au plus, 260 par seconde quelle que soit la fréquence d'images (jeu complet ~10 fois par seconde, report fractionnaire) ; plein air si ciel 15 à la tête ou ≥ 40 % des rayons montants/horizontaux s'échappent sous un ciel ≥ 8 ; sinon portée moyenne ≥ 9 → grande caverne, sinon petite grotte (sous terre) ou intérieur. Envoyé au mixeur seulement quand il change.
- **Réverbération maison façon Freeverb** (Jezar, domaine public), sans dépendance : 8 peignes amortis en parallèle + 4 passe-tout en série par oreille (décalage stéréo 23 échantillons), délais mis à l'échelle de la fréquence du périphérique ; rétroaction ≤ 0,92 et amortissement → queue toujours décroissante (testé : 6 s après une impulsion, −60 dB ; bruit plein pot sans emballement). Réglages par lieu **dans le pack** (`spaces/outdoors|interior|small_cave|large_cavern.ron` : rétroaction ≤ 0,97, amortissement, mouillé ; bornés au chargement ; un lieu absent ne résonne pas) — `strata` : plein air sec ; intérieur 0,76/0,18 ; petite grotte 0,84/0,30 ; grande caverne 0,92/0,42 en rétroaction/mouillé — envoyés au mixeur comme salle (`Command::Room`) et glissés de 15 % par bloc ; couper l'audio spatial efface la queue. Seules les voix positionnées y sont envoyées (pas les fonds). Non calculée quand le mouillé est nul (plein air) : lignes vidées avant de resonner.
- **Étouffement** : segment son → oreille échantillonné tous les demi-blocs (64 points, 32 blocs au plus), cellules distinctes, sans celles du son et de l'oreille ; étouffement = 1 − e^(−0,8 × densités cumulées). Mixeur : passe-bas à un pôle de 20 kHz à 350 Hz (géométrique) et −75 % de volume au maximum, rampés par bloc ; contourné exactement à 0. Calculé au départ du son, puis 10 fois par seconde pour les sons en cours (identifiant de voix donné par le jeu, `Command::Muffle`).
- **Réglage « Audio spatial »** (`settings.sound.spatial` : `advanced` / `simple`, onglet Son, fr/en/lol). Le seul réglage de son touché par les **préréglages** : stéréo simple pour **DS** et **très bas**, avancé pour les autres ; le changer à la main fait passer en « personnalisé » comme un réglage graphique. En stéréo simple, ni rayons ni étouffement côté jeu, ni réverbération ni filtre côté mixeur (sortie identique à un mixeur sans lieu, testé).
- **Coût** (banc `audio`, 32 voix dont la moitié étouffées + 4 fonds, bloc de 512 trames ≈ 11,6 ms, cloud) : **155 µs avancé, 87 µs stéréo simple**, soit ~1,3 % et ~0,75 % d'un cœur.

## D055 — Musique procédurale : thèmes en pack, rendu par blocs en arrière-plan, cache WAV, rare et calme (v0.2, jalon 10)

- **Thèmes en pack** (`music/<nom>.ron`, chargés dans `core::audio` avec les sons, `Sounds::themes`) : dimensions où on l'entend, écran titre, tonique MIDI, mode (7 modes, 2 pentatoniques ou `Custom`), tempo, nombre de morceaux, durée, densité, silences, degrés des accords, motifs (degrés + durées en temps), piano, nappe, réverbération, volume ; valeurs **bornées au chargement** (durée ≤ 240 s, 16 morceaux, 16 motifs de 16 notes…) avec une erreur de pack par valeur corrigée. Le thème est rattaché aux dimensions par le thème lui-même (pas de champ dans `dimensions/*.ron`) : aucun changement du protocole, le client connaît déjà sa dimension. Thème de Terra : ré lydien, 66 bpm, 5 morceaux de 75 à 170 s.
- **Composition pure et déterministe** (`compose(def, graine, Mood)`) : phrases de 1 à 3 motifs variés (rétrograde, renversement, augmentation, décalage d'un degré, 12 % de notes respirées) sur un accord tiré parmi `chords`, note grave et accord de nappe au hasard ; après chaque phrase, fin de la résonance + 2,5 s de queue + silence tiré (× 1,5 − densité). Rien ne sonne après la fin ; graine = FNV de l'identifiant ⊕ numéro du morceau. Mesuré sur les 5 morceaux de Terra : **47 à 68 % de silence** (fenêtres de 100 ms sous −46 dB).
- **Synthèse sans `sin`** : chaque partiel est un phaseur tournant en `f64` (deux multiplications-additions par échantillon, décroissance incluse dans la rotation). Piano : 8 harmoniques étirées (inharmonicité 0,0004), décroissance d'autant plus rapide que l'harmonique est haute, notes graves plus longues, deuxième corde désaccordée pour les deux premières, bruit de marteau filtré 30 ms, étouffoir 0,6 s. Nappe : 3 harmoniques × 2 désaccords, passe-bas, tremolo lent. Réverbération Schroeder mono (4 peignes amortis, 2 passe-tout) propre au rendu, limiteur doux (linéaire jusqu'à 0,7, jamais 1), fondu final 1,5 s.
- **Rendu par blocs** (`PieceRenderer::fill`, 4 096 échantillons) écrit directement en WAV 16 bits mono 44,1 kHz : jamais le morceau entier en mémoire (quelques centaines de Ko). Le rendu par blocs et le rendu complet sont identiques (testé).
- **Cache** : `<données>/cache/music/<ns>-<thème>-<humeur>-<n>-a<ALGORITHM>-<empreinte>.wav`, l'empreinte étant un FNV de chaque champ du thème, un par un (`fingerprint.rs`, pas l'affichage `Debug`) : changer l'algorithme (`ALGORITHM`) ou une valeur du thème donne un autre fichier ; les fichiers des thèmes connus qui ne correspondent plus à rien (et les `.part` de plus de 15 min, un autre jeu pouvant écrire les récents) sont effacés au démarrage du fil de rendu et à chaque rechargement des packs. Écriture dans un `.part` propre au processus et au rendu (`<nom>.<pid>-<n>.part`), `fsync` puis renommage. **WAV non compressé** plutôt qu'Ogg/zstd : aucune dépendance d'encodage, lecture en flux triviale, ~88 Ko/s (8 à 15 Mo par morceau, ~50 Mo pour Terra) : c'est du disque, pas de la RAM.
- **Mesures** (cloud, release) : rendu d'un morceau de 90 à 167 s en **0,14 à 0,32 s** ; outil `--render-music` (morceau entier en mémoire + image) à 74 Mo de RSS au plus. En jeu : un seul fil `music-render` pour toute la session, démarré à la première demande et gardé au rechargement des packs (génération incrémentée : les demandes et résultats d'avant sont ignorés), un morceau à la fois (priorité normale : pas d'API standard pour la baisser), pendant le silence qui précède (jamais au chargement ni sur le fil principal) ; lecture par un fil `music-read` qui envoie des blocs de 0,5 s au mixeur (4 d'avance, canal borné) ; le mixeur ne bloque jamais (bloc en retard = silence).
- **Planification** (`MusicSchedule`, pur) : écran titre 2 à 5 s puis un morceau ; dans un monde, première attente = 10 % de l'attente normale, puis **fréquence de la musique** (`settings.sound.music_frequency` : rare 10–20 min, normale 5–10, souvent 2–5 ; hors préréglages). Le compte à rebours s'arrête en pause (le morceau en cours continue, comme Minecraft) ; un changement de titre ↔ monde fait un fondu de sortie et recommence l'attente ; un changement de dimension laisse finir le morceau. Un `Start` refusé (file pleine) est redemandé à l'image suivante ; un flux lâché n'importe où (y compris une commande perdue) lève son drapeau de fin (`Drop` de `MusicFeed`) et relance l'attente. Fondu d'entrée/sortie 3 s dans le mixeur (catégorie musique, centré, sans réverbération du lieu).
- **Désactivation** : volume de la musique (ou général) à 0, ou pas de périphérique : ni rendu, ni lecture, ni fichier (testé). Pas de valeur « jamais » dans la fréquence : le volume suffit et reste un seul geste.
- **Musique adaptative préparée** : `Mood` (seulement `Calm`) fait partie de la composition et du nom de fichier ; la v0.4 ajoutera une intensité de combat sous forme de couches rendues sur la même partition (fichiers parallèles mixés en phase), sans changer le cache ni le mixeur au-delà d'un flux de plus.
- **Remplacement par `.ogg`** : `music/<thème>/*.ogg` (ou `music/<ns>/<thème>/`) dans un pack ; le dossier du pack le plus haut remplace les morceaux composés du thème (un fichier tiré au hasard, jamais deux fois de suite) ; décodé en flux par `rodio`, mélangé en mono, converti à 44,1 kHz par blocs avec position et dernier échantillon reportés d'un bloc à l'autre (identique à la conversion d'un seul tenant, testé). Un dossier sans thème `.ron` est une erreur de pack.
- **Outil** : `strata --render-music <dossier>` écrit chaque morceau en WAV et une image (forme d'onde, fond rouge sombre sur les silences ; spectrogramme par demi-ton par Goertzel) pour vérifier silences et notes sans écouter.

## D056 — Types de monde en pack, réglages de génération appliqués par-dessus le pack, codes `S1-` (v0.2, jalon 11)

- **Réglages** (`core::generation::WorldgenSettings`, sérialisable, partagé par `NewWorld` et `world.ron` avec `#[serde(default)]` : un ancien monde est « normal », sans réglage) : type de monde (identifiant), taille des biomes, densité des grottes, fréquence des minerais (filons et gisements) et densité des structures (lue à partir de la v0.6) **en pourcentages entiers** (aller-retour exact, égalité stricte), niveau de la mer optionnel (aucun = celui de la dimension), biome et couches optionnels (aucun = ceux du type). Monde plat : mer à 0 (tout est terre ferme), échantillon constant, biome forcé, arbres et plantes seulement si `features`.

- **Codes** : `S<version>-` + base32 de Crockford (sans lettres ambiguës ; casse, espaces et tirets ignorés ; O→0, I/L→1) de `postcard` d'une structure `CodeV1` figée (identifiants du pack `strata` sans espace de noms) + somme de contrôle FNV de 16 bits. Code par défaut : 29 caractères. Code abîmé = `CodeError::Malformed`, version plus récente = `CodeError::FutureVersion`, avec messages Fluent (`world-code-*`) ; types, biomes et blocs inconnus = `SettingsError` (`world-settings-*`). Jamais de panique. `postcard` ajouté à `core` (déjà utilisé par le serveur).

## D059 — Clics de bloc numérotés, mis en file sur le serveur et prédits par le client (v0.2.1, jalon 4)

- **Constat confirmé** : le serveur ne faisait qu'une action toutes les 2 ticks (`ACTION_TICKS`) et **jetait en silence** un clic arrivé plus tôt (deux clics rapprochés ne posaient qu'un bloc) ; le client n'affichait le bloc qu'à la réponse.
- **Protocole** (version 8) : `BreakBlock`, `PlaceBlock` et `UseItem` deviennent `ClientMessage::BlockAction { id: ActionId, action: BlockAction }` (`Break`, `Place`, `Use`), numérotés à partir de 1 par client. Le serveur répond toujours `ServerMessage::ActionDone(id)`, après les `BlockChanged` du clic ; un clic **refusé** (rien n'a changé) renvoie d'abord l'état réel de la case visée et de sa voisine du côté de la face, ce que le client a pu prédire.
- **Serveur** (`game/actions.rs`) : la limite de 10 actions par seconde reste ; un clic trop tôt (ou derrière d'autres en attente) va dans une file par joueur (`PlayerControl.actions`), bornée à 8 (`MAX_QUEUED_ACTIONS`, au-delà : refus avec réponse), et un clic au plus en sort par tick quand la limite le permet, dans l'ordre. Toutes les validations (portée, case libre, support, dureté, objet tenu) sont faites au moment de l'exécution. La boîte de messages du jeu (`take_messages`, ex-`take_entity_messages`) porte aussi les réponses, envoyées après les changements de blocs.
- **Client** (`prediction.rs`, `WorldView::predict/receive_block/acknowledge`) : casser et poser sont prédits avec les règles du serveur (dureté hors créatif, case visée, plante remplaçable, variante orientée, support via `UpdateRules`, pas dans le corps du joueur ; portée laissée au serveur) ; seau, briquet et bateau ne le sont pas. Le bloc prédit est affiché tout de suite (remaillage, lumière provisoire D046) avec son et particules (D052, D053). Une case prédite garde son bloc jusqu'à la réponse du **dernier** clic qui l'a prédite ; les `BlockChanged` qui la touchent entre-temps sont seulement retenus (dernier état connu du serveur). À la réponse, la case prend cet état, **sans effet** (pas de double son à la confirmation, rien au refus) ; ainsi une prédiction écrasée par une mise à jour plus récente ne revient pas. Une colonne reçue ou oubliée efface ses prédictions. Pas de réglage : coût négligeable (une table par clic en vol).
- **Alternatives écartées** : réduire `ACTION_TICKS` à 1 (déplace le problème au double-clic dans le même tick) ; prédiction sans accusé, corrigée par le seul `BlockChanged` (un refus ne se verrait jamais, et une réponse en retard ferait clignoter le bloc) ; un accusé par case plutôt que par clic (plusieurs clics sur la même case se mêlaient).
- **Tests** : serveur (`game/actions/tests.rs`) : deux clics rapprochés posent deux blocs, refus = état réel puis réponse, clic en file encore validé, file pleine = réponse immédiate et ordre gardé ; client (`prediction/tests.rs`) : prédiction affichée puis confirmée sans double son, refus défait sans effet, casse prédite avec une seule gerbe et un seul son, changement serveur plus récent gagnant, changements non prédits affichés à part, règles de prédiction de casse et de pose.
